# ระบบสร้างภาพโปสเตอร์

## 🔴 กฎข้อแรก — เห็นของแปลกในภาพ อย่าเพิ่งโทษโมเดล

**เช็ควัตถุดิบที่เราป้อนเข้าไปก่อนเสมอ**

เคสจริง 20 ส.ค. 2026: ภาพออกมามีลายน้ำ "DIVISION X CARD" ปั๊มบนหน้าซอง
สรุปทันทีว่าโมเดลแปะเอง แล้วเขียนคำสั่งห้าม overlay เพิ่มเข้าไป

**ผิด** — ซูมดูรูปต้นทางใน Supabase แล้วพบว่า**รูปของเรามีลายน้ำอยู่แล้ว**
โมเดลแค่ลอกมาตามที่สั่งให้ลอกให้เหมือน คำสั่งที่เพิ่มไปจึงขัดกับคำสั่งเดิม
และอาจทำให้โมเดลเริ่มแก้ซองแทนที่จะลอก

> ✅ **แก้จบแล้ว 25 ส.ค. 2026** — เจ้าของส่งรูปไดคัทไม่มีลายน้ำมาครบ 90 ไฟล์
> อัปโหลดทับของเดิมทั้งหมดแล้ว **45 จาก 47 SKU มีทั้งรูปซองและรูปกล่องที่สะอาด**
> (ขาดแค่ FB 07 กับ YGH The Heroes ซึ่งไม่เคยลงตู้)
>
> รูปใหม่เป็น WebP 1024px พื้นหลังโปร่ง (RGBA) ไฟล์ละ 77–195 KB
> ต้นฉบับ PNG 8-12 MB ต่อไฟล์ **ใหญ่เกินขีดจำกัด 6 MB ของตัวสร้างภาพ** จึงต้องย่อก่อนเสมอ
> ถ้าวันหน้าเพิ่มรูปใหม่ อย่าลืมย่อ ไม่งั้น `fetchRef()` จะทิ้งเงียบ ๆ แล้วโมเดลจะแต่งลายซองเอง

**บทเรียนเดิมที่ยังใช้ได้:** ก่อนหน้านี้ลายน้ำสลับกันไปมาแม้ในค่ายเดียวกัน
(OP 01 มี · OP 16 ไม่มี · EB 01 มี) และเคยเข้าใจผิดว่าโมเดลเป็นคนแปะเอง
ทั้งที่รูปต้นทางมีมาแต่แรก — **เห็นของแปลกในภาพ ให้ซูมดูรูปต้นทางก่อนเสมอ**

## 🔴 กฎข้อสอง — ลำดับใน prompt เปลี่ยนผลลัพธ์จริง

ไม่ใช่แค่ความเรียบร้อยของโค้ด **สิ่งที่อยากให้ชนะต้องอยู่ท้ายสุด**

พิสูจน์แล้วด้วยการยิงสองรอบ เนื้อหา prompt เหมือนกันทุกตัวอักษร ต่างแค่ตำแหน่ง:

| ลำดับ | ผลลัพธ์ |
|---|---|
| ไอเดียภาพขึ้นก่อน → กฎแบรนด์ 29 ข้อตามหลัง | **ซองสองใบลอยเฉย ๆ** กฎข้อ "สินค้าต้องกิน ≥60% ของเฟรม" ชนะ |
| กฎแบรนด์ขึ้นก่อน → **ไอเดียปิดท้าย** | ภาพแบ่งจอ สองฝั่งคนละบรรยากาศ ตรงกับเนื้อหา |

ตอนนี้ `buildPrompt()` วางไอเดียไว้ท้ายสุดพร้อมประโยค
*"This idea outranks the brand signature, the suggested direction and every stylistic habit above …
The HARD RULES and FACTS still apply without exception."*

⚠️ **ประโยคนี้ต้องแยก "สไตล์" ออกจาก "กฎเหล็ก" เสมอ** — เดิมเขียนว่า
*"If a brand rule would flatten it into a plain product shot, follow the idea"*
ซึ่งถูกตอนที่ brandRules เป็นกฎสไตล์ แต่ 14 ก.ย. 2026 ตัวแปรเดียวกันกลายเป็นกฎเหล็ก
(ซองจริง · ไทยถูก · ห้ามแต่งตัวเลข) ประโยคเดิมจึงกลายเป็น**ใบอนุญาตให้แหกกฎเหล็กเพื่อไอเดีย**
— จับได้ตอนไล่ diff ก่อน deploy ไม่ใช่จากภาพที่พัง

⚠️ **ปิดประตูนั้นแล้ว ของที่พึ่งมันอยู่พังตาม** (15 ก.ย. 2026) — `ALLOWED CARDS` (รายชื่อการ์ดจริงใน FACTS
ตั้งแต่ 28 ส.ค.) ขัดกับกฎเหล็กข้อ 1 ที่ห้ามวาดลายการ์ด/ตัวละครมาตลอด แต่ใช้ได้เพราะประโยคเดิมให้ไอเดียชนะ
พอกฎเหล็กชนะทุกกรณี โมเดลเลี่ยงการ์ด → ภาพสอนกฎ #43 เอา*การ์ดพลังงาน*ลงเบนช์แทนโปเกมอน = สอนผิด

เจ้าของเลือกให้วาดหน้าการ์ดจริงที่ระบุได้ · ข้อยกเว้นต้องเขียน**ที่ตัวข้อห้ามทุกจุด**
(กฎเหล็กข้อ 1 · `negative_always` · ตัวคิดไอเดีย) ไม่ใช่แค่ใน FACTS
และตัวคิดไอเดียต้องได้รายชื่อ*ก่อน*คิด ไม่ใช่หลังคิด

> **จะปิดทางหนีของกฎ ให้ grep ก่อนว่ามีบล็อกไหนพึ่งทางนั้นอยู่**

**อย่าย้ายมันขึ้นไปข้างบนเพื่อความสวยงามของโค้ด**

## 🔴 กฎข้อสาม — บรีฟต้องบอกทั้ง "ของ" และ "สิ่งที่อยู่ในของ"

เคสจริง 21 ส.ค. 2026: เจ้าของบอกว่าภาพตู้ "มีสินค้าอยู่ประเภทเดียวทั้งตู้
ดูไม่ค่อยน่าเชื่อถือ เพราะตู้ของเราขายสินค้าหลายอย่าง"

พรอมต์บรรยาย**ตัวตู้**ไว้ละเอียดมาก — กรมท่า กระจกหน้า 6 ชั้น รางแขวน จอสัมผัสขวา
แถบ PUSH & PICK ล่าง สั่งขนาดนั้นแล้วยังได้ภาพที่ผิด เพราะ**ไม่เคยบอกว่าข้างในมีอะไร**
โมเดลเลยเลือกทางที่ง่ายที่สุด: ก็อปซองเดียวกันใส่ทุกช่อง

> บรรยายวัตถุละเอียดแค่ไหนก็ไม่พอ ถ้าไม่บอกว่า**อะไรอยู่ในนั้น อยู่กี่อย่าง อยู่ยังไง**
> ทุกช่องว่างที่เราไม่ระบุ โมเดลจะเติมด้วยทางที่ง่ายที่สุด ไม่ใช่ทางที่จริงที่สุด

### ตัวเลขจริงที่ต้องใช้บรีฟ — อย่าเดา อย่าปัดเลข

| เรื่อง | ของจริง | เช็คจากไหน |
|---|---|---|
| จำนวนสาขา | **12 ตู้** (`status=active`) | `machines` |
| สินค้าต่อตู้ | **28–38 ชนิด** จาก ~55 ช่อง | `machine_stock` |
| ชนิดที่กินช่องมากสุด | **7 ช่อง = 12–13%** ไม่เคยเกินนี้ | `machine_stock` |
| เวลาเปิด | ตามเวลาห้าง · ขายได้ทุกวัน (60/60 วัน) | `sales` |
| ค่าสถานะการ์ด | `deploy/tasks/opcg_cards.json` | ทางการฉบับไทย |

ตัวเลขพวกนี้เปลี่ยนได้ **ตรวจใหม่ทุกครั้งก่อนเขียนลง prompt** อย่าลอกจากตารางนี้ไปดื้อ ๆ

## 🔴 กฎข้อสี่ — ข้อความที่โมเดลเชื่อมาจาก 3 แหล่ง กวาดแหล่งเดียวไม่พอ

| แหล่ง | คืออะไร |
|---|---|
| `deploy/tasks/image_style.json` | สไตล์ · ข้อห้าม · กฎภาษาไทย |
| `image/route.js` → `facts[]` | ข้อเท็จจริงธุรกิจที่ส่งไปทุกใบ |
| `lib/artDirector.js` → `HARD RULES` | สิ่งที่ตัวคิดฉากเชื่อ ก่อนจะคิดไอเดียด้วยซ้ำ |

เคสจริง: ลบคำว่า "เปิด 24 ชม." ออกจากเทมเพลตโปสเตอร์ทั้ง 5 แบบแล้ว
แต่ยังเหลือ `"open 24 hours"` ใน `facts[]` และ `"self-serve, 24 hours"` ใน `HARD RULES`
→ **ตัวเขียนกับตัววาดยังเชื่อว่าเราเปิด 24 ชม. อยู่ดี แล้วเขียนกลับมาเองได้เรื่อย ๆ**

⚠️ **กวาดสองภาษาเสมอ** — รอบแรกค้นแต่ `24 ชม.` เลยไม่เจอ `24 hours` ทั้งสองจุด

```bash
grep -rn "24 ชม\|24 ชั่วโมง" deploy/tasks/ deploy/app/ deploy/lib/
grep -rn "24 hours\|24-hour\|24/7\|round the clock" deploy/tasks/ deploy/app/ deploy/lib/
```

## 🔴 กฎข้อห้า — คำกริยาในแคปชั่นถูกวาดตรงตัว

แคปชั่นเขียนว่า *"มือสั่นตั้งแต่**ฉีก**ซอง"* → ตัวคิดฉากสั่งวาดมือฉีกซอง
→ ได้ภาพซองขาดยับ + มือที่สามโผล่มามุมขวาล่าง

**มือคือจุดที่โมเดลวาดพลาดบ่อยที่สุด** แต่ `negative_always` เดิมมีแค่
*"no people's faces"* ไม่มีคำสั่งเรื่องมือเลยสักคำ

ตอนนี้ `negative_always` มี 7 ข้อ — คุมซองต้องปิดผนึกไม่ขาด · มือไม่เกินสองข้างและถูกกายวิภาค
· การ์ดต้องแบนเรียบ **ห้ามตัดออก**

> แคปชั่นที่มีคำว่า ฉีก · แกะ · เปิดซอง · กระชาก คือสัญญาณให้ตรวจภาพที่ได้เป็นพิเศษ

## 🔴 กฎข้อหก — ภาพไม่สมจริง ให้หาข้อมูลจริงในฐานข้อมูลก่อนคิดไปหาในเน็ต

เจ้าของถามว่าควรให้ Hermes ไปค้นข้อมูลสถานที่บนอินเทอร์เน็ตก่อนบรีฟไหม
คำตอบคือ **ไม่ต้อง — ของที่แม่นกว่าอยู่ในฐานข้อมูลเราแล้ว**

`machines.config.branch` มี `display_name` · `floor` · `landmark` ครบทั้ง 12 สาขา
ระดับ *"ไอคอนสยาม ชั้น 6 หน้าร้าน Karun Thai Tea"* — เป็นของที่คนไปติดตั้งตู้จดเอง
**หาในอินเทอร์เน็ตไม่เจอ** เน็ตให้ได้แค่ "ไอคอนสยามเป็นห้างริมเจ้าพระยา" ซึ่งกว้างเกินใช้

ปัญหาไม่เคยอยู่ที่ "ไม่มีข้อมูล" แต่อยู่ที่ **ข้อมูลไม่ถูกส่งเข้าบรีฟ** —
เดิม route ดึง `machines` มานับความยาว array แล้วส่งไปแค่เลข `12` ตัวเดียว
โปสเตอร์ #35 จึงวาดตู้ริมถนนกลางคืน ทั้งที่แคปชั่นเขียนว่าเดินอยู่ในไอคอนสยาม

> เจอภาพเพี้ยนเรื่องสถานที่/สินค้า/จำนวน — ไล่ก่อนว่าข้อเท็จจริงข้อนั้น
> **เดินทางไปถึง prompt จริงไหม** อย่าเพิ่งเขียนกฎใหม่ทับ

**และ Hermes เรียกจากตรงนี้ไม่ได้อยู่แล้ว** — route สร้างภาพรันบน Vercel
ส่วน Hermes เป็น Telegram gateway บนเครื่องเจ้าของ Vercel ยิงเข้าไม่ถึง
อะไรที่ต้องใช้ตอนสร้างภาพ ต้องอยู่ในฐานข้อมูลหรือใน `tasks/*.json`

## 🔴 กฎข้อเจ็ด — กฎสไตล์ห้ามส่งเป็นคำบังคับ ไม่งั้นทุกภาพหน้าตาเดียวกัน

เคสจริง 14 ก.ย. 2026: เจ้าของบอกว่าบรีฟ *"บังคับ AI ออกแบบมากเกินไป ไม่มีอิสระ ภาพจำเจ"*

ยิงขั้นคิดไอเดียกับแคปชั่นจริง 6 ใบก่อนแก้ — **เนื้อหาไอเดียต่างกัน แต่หน้าตาภาพสูตรเดียวกัน**:
6/6 มือถือซองเรียงพัด · 6/6 พื้นกรมท่า 1080x1350 · 5/6 ตู้กลางห้าง + สินค้ากิน 60% ·
6/6 วางข้อความสูตรเดิม (พาดหัวหนึ่งในสามบน → แท็ก → กล่องข้อมูล → บรรทัดวันที่ล่างสุด)

ต้นเหตุ: กฎ 30 ข้อใน `art_direction.json` ถูกส่งเข้า**ทั้งขั้นคิดไอเดีย (สั่ง "obey all") และขั้นวาด**
โดยไม่แยกว่าข้อไหนคือ*ความจริงที่ห้ามพลาด* ข้อไหนคือ*สูตรสไตล์* · บวกเมนูท่า 7 แบบ ·
บวกประโยค "มือถือซองพัด ใช้ได้เลย" → โมเดลหยิบของที่ได้รับอนุญาตชัดที่สุดทุกครั้ง

> **โมเดลเคารพทุกข้อที่เห็นแบบตามตัวอักษร** กฎสไตล์หนึ่งข้อ = ภาพทุกใบมีสิ่งนั้น
> ยิ่งเขียนละเอียด ยิ่งได้ภาพเหมือนกัน

แยกใหม่เป็น 3 ชั้น:

| ชั้น | คีย์ | ส่งยังไง |
|---|---|---|
| กฎเหล็ก | `hard_rules` | ห้ามละเมิด — ข้อเท็จจริง กฎหมาย ภาษาไทย |
| ลายเซ็นแบรนด์ | `brand_signature` | บอกว่า "ต้องมีอะไร" ไม่บอกว่า "ต้องจัดยังไง" |
| แนวภาพ | `style_directions` | หมุนตาม id ส่งเป็น**ข้อเสนอ** ตัวคิดไอเดียเปลี่ยนได้ |

กฎสไตล์เดิมย้ายไป `retired_rules` (ไม่มีโค้ดอ่านโดยตั้งใจ)

**จะเพิ่มกฎใหม่ ถามก่อนว่า "ถ้าละเมิดแล้วผิดความจริงหรือผิดกฎหมายไหม"** ถ้าแค่ไม่สวย ไม่ใช่กฎเหล็ก
→ ใส่เป็นแนวภาพแทน

### ⚠️ กฎที่สั่งให้ "มีช่อง" แต่ไม่ให้ข้อมูล = โมเดลแต่งข้อมูลเอง

กฎสไตล์เดิมข้อ 12 สั่ง *"contact strip: 3 rounded capsules along the bottom edge"*
แต่ไม่เคยมีข้อมูลติดต่อจริงใน FACTS → โปสเตอร์จริง 4 ใบมี**เบอร์โทรไม่ซ้ำกันเลยสักใบ**
และมีเว็บ `www.divisionxcard.com` ที่ไม่มีอยู่จริง · TEXT LOCK ก็กันไม่อยู่ เพราะกฎสองข้อสั่งขัดกัน

→ เพิ่มกฎเหล็กห้ามเบอร์/เว็บ/QR/บัญชีโซเชียลที่ไม่ได้ให้ไป · **ตรวจภาพเก่าก่อนโพสต์ซ้ำ**

## กับดักที่เคยทำให้พังจริง

### 1. fallback ที่กลืน error แล้วเดินต่อเงียบ ๆ

`askOpenAI()` วนลองโมเดลหลายตัว เจอ 400 ที่ข้อความมีคำว่า `model` จะ `continue`

เอกสาร OpenAI ระบุว่า **`gpt-image-2` ห้ามส่ง `input_fidelity`** แต่โค้ดส่งไปทุกโมเดล
error ที่ได้คือ *"The model 'gpt-image-2' does not support the 'input_fidelity' parameter"*
ซึ่ง**มีคำว่า model** → เข้าเงื่อนไข → เลื่อนไป `gpt-image-1.5` เงียบ ๆ

**ผลคือภาพทุกใบมาจาก gpt-image-1.5 ไม่เคยเป็น gpt-image-2 เลยสักใบ**
แล้วทีมสรุปว่า "gpt-image ทำไม่ได้" ทั้งที่ไม่เคยเรียกตัวที่ตั้งใจจะใช้ติดเลย

→ ตอนนี้ route คืน `attempts[]` กับ `usage` ออกมาทุกครั้ง **ดูทุกครั้งว่าภาพมาจากโมเดลไหนจริง**

**14 ก.ย. 2026 ปิดรูนี้เพิ่มอีกสองชั้น** (ตอนเปลี่ยนเป็น gpt-image-2.5-flare):

- `input_fidelity` ส่งเฉพาะรุ่นใน `openai_input_fidelity_models` (**รายชื่อที่อนุญาต**)
  เงื่อนไขเดิม `!/^gpt-image-2/` รอดมาได้เพราะชื่อรุ่น 2.5 บังเอิญขึ้นต้นเหมือนกัน รุ่นหน้าที่ชื่อต่างจะพังซ้ำ
- 400 ที่มี `error.param` และไม่ใช่ `model` → throw ออกไปให้เห็นทันที ไม่เลื่อนรุ่น

⚠️ **เช็คฟรีด้วยการส่งค่าผิดใช้ไม่ได้ผล** — API ตรวจ "ค่า" ก่อน "รุ่นรองรับไหม"
แม้แต่ gpt-image-2 ที่รู้แน่ว่าปฏิเสธ `input_fidelity` ก็ตอบเหมือนรุ่นที่ยังไม่รู้คำตอบ
อยากรู้ว่ารุ่นใหม่รับพารามิเตอร์ไหน ต้องยิงให้วาดจริง

### 2. dead config — คีย์ที่มีในไฟล์แต่ไม่มีใครอ่าน

เจอมาแล้ว 5 ตัว:

| คีย์ | ผลตอนที่ตายอยู่ |
|---|---|
| `style.with_reference` | คำสั่ง "ห้ามวาดซองใหม่" ไม่เคยถูกส่ง → โมเดลวาดซองปลอม |
| `style.scenes` | 9 ฉากแยกตามรูปแบบโพสต์ ไม่เคยถูกใช้ |
| `content_format` | ไม่เคยส่งเข้า prompt |
| `skus.franchise` | มีข้อมูลครบ 9 ค่าย ไม่เคยถูกใช้ |
| `art_direction.json` | สร้างไว้แล้วเป็นไฟล์ลอยอยู่วันนึง |

> **เพิ่มคีย์ใหม่ในไฟล์ตั้งค่าแล้วต้อง grep ยืนยันว่ามีโค้ดอ่านจริง** ไม่งั้นมันจะดูเหมือนทำงานอยู่

### 3. คำสั่งขัดกันเองใน prompt เดียว

โหมด `full` เคยสั่ง `thai_rule` ("วาดข้อความไทยนี้ให้ตรงทุกตัวอักษร")
แล้วต่อท้ายด้วย `negative` ที่มี `"no text, no letters, no words"` — ทำพร้อมกันไม่ได้

→ แยกเป็น `negative_always` กับ `negative_no_text` แล้ว **ห้ามรวมกลับ**

### 4. โมเดลเติมข้อความไทยที่ไม่ได้อนุมัติ

`facts_rule` เดิมพูดถึงแค่ "ตัวเลข" ไม่ได้ห้าม "คำ" โมเดลจึงแถมป้ายไทยมาเอง

**ปัญหาไม่ใช่ว่ามันเขียนผิด** — รอบที่เจอมันเขียนถูกด้วยซ้ำ
แต่แปลว่า**ข้อความที่ไม่เคยผ่านด่านตรวจคำเว่อร์ขึ้นภาพได้** (ดู `dvx-content` → `overclaim`)

→ เพิ่มบล็อก **TEXT LOCK** ห้ามเด็ดขาด ยิงจริงแล้วเหลือแค่บรรทัดที่อนุมัติ

### 5. ธีมค่ายเดียวยัดให้ทุกโพสต์

`route.js` เคยฮาร์ดโค้ด *"a One Piece nautical theme"* ไว้ในทุก prompt
บวกกับ `poster_concepts` default = `treasure` (ล่าสมบัติ One Piece)

→ โปสเตอร์ **Dragonball FB-09** ออกมามีสมอ คลื่น เข็มทิศ นกนางนวลเต็มใบ

**⚠️ ตัดแค่ `decor` ไม่พอ** — ชื่อคอนเซปต์เองคือ "ล่าสมบัติ One Piece" ซึ่งถูกส่งไปทั้งบรรทัด
ต้องตัดทั้งบล็อกเหลือแค่ทิศทางสีเมื่อค่ายไม่ตรง

ลายเดินเรือ**ผูกกับตัวตู้จริงเท่านั้น** (ตู้พิมพ์ลายนั้นจริง) ห้ามลามเป็นกรอบ/พื้นหลัง

### 6. ชื่อไฟล์ไม่ตรงชนิดตอนส่ง multipart

รูปซองใน Supabase มีทั้ง WebP และ JPEG แต่โค้ดเคยตั้งชื่อ `ref0.jpg` ให้ทุกอย่างที่ไม่ใช่ PNG

## ข้อจำกัดที่ยังแก้ไม่ได้ — อย่าสัญญากับเจ้าของ

**"ตัวอักษรไทยถูก 100%" รับประกันไม่ได้ถ้าโมเดลเป็นคนวาด**

เอกสาร OpenAI ยังลิสต์ Text Rendering เป็น Limitation และไม่เคยเอ่ยถึงภาษาไทยเลยสักคำ
ทดสอบผ่าน 2-3 ใบไม่ใช่หลักฐานว่าผ่านตลอด

**คำว่า 100% จะจริงเชิงโครงสร้างก็ต่อเมื่อ Chromium เป็นคนวางตัวอักษร**
→ นั่นคือ `poster_mode: "art"` (AI วาดแค่ฉาก เทมเพลตวางข้อความ) หรือ `poster_render.py`

`image_style.json` ตั้ง `poster_mode: "full"` เพราะเจ้าของชอบแบบนั้น **ห้ามสลับเองโดยไม่ถาม**

**ซองที่ได้เป็นการวาดซ้ำที่เหมือนมาก ไม่ใช่การแปะรูปจริง** — ตัวหนังสือบนซองถูกครบ สีตรง
แต่ลายอาร์ตไม่ใช่พิกเซลเดียวกับต้นฉบับ ถ้าต้องการเป๊ะระดับพิกเซล ต้องใช้เทมเพลตแปะ

## เช็คลิสต์ก่อนส่งภาพให้เจ้าของดู

เรนเดอร์ฟรี ไม่เสียค่า API ใช้ฉาก AI ที่มีอยู่แล้ว:

```bash
py -3 deploy/agents/poster_render.py --id <id> --dry-run --out ตรวจ.png
```

แล้วเปิดดูจริง **อย่าตรวจด้วยการอ่านโค้ด** — ทั้งสองเคสข้างบนอ่านโค้ดแล้วดูปกติทั้งคู่

- [ ] ตู้มีสินค้าหลายชนิดไหม (ไม่ใช่ซองเดียวเต็มตู้)
- [ ] มือ — ไม่เกินสองข้าง นิ้วครบ ไม่มีมือลอย
- [ ] ซอง — ปิดผนึก ไม่ขาด ไม่ยับ
- [ ] ตัวเลขในภาพตรงกับฐานข้อมูลไหม (สาขา · ค่าสถานะการ์ด)
- [ ] ป้ายล่างไม่ล้นแถว (แถบตั้ง `nowrap` ยาวเกินแล้วเบี้ยวทั้งแถว)
- [ ] คำไทยไม่ถูกตัดกลางคำตอนขึ้นบรรทัดใหม่
- [ ] โทนสีตรงกับแบรนด์ (ฟ้านีออนบนกรมท่า) — คอนเซปต์ `battle` ออกมาเป็นสีแดง

## รูปตู้จริง — แนบแล้ว แต่ต้องเข้าใจเงื่อนไข

เดิม `route.js` แนบรูปตู้เฉพาะตอน `concept` เป็น `machine_luck`/`real_machine`
แต่หน้าเว็บไม่เคยส่ง `concept` มา → ตกไปที่ default ทุกครั้ง = โมเดลไม่เคยเห็นรูปตู้จริง

**แก้แล้ว** — ตอนนี้ตัดสินใจ*หลัง*ได้ไอเดียภาพ ตัวคิดไอเดียตอบคีย์ `shows_machine` (true/false) มาเอง
ถ้า true จึงแนบ · ไม่แนบพร่ำเพรื่อเพราะรูปอ้างอิงเพิ่มค่า input จริง และรูปตู้ดึงตู้เข้าภาพ

⚠️ **อย่ากลับไปใช้ regex จับคำเป็นตัวตัดสินหลัก** (15 ก.ย. 2026) — `MACHINE_WORDS` จับ *"no vending machine"*
กับ *"ช่องว่าง"* ได้เหมือนกัน หลังปลดล็อกบรีฟ ตัวคิดไอเดียถูกบอกให้เลี่ยงตู้ ประโยคปฏิเสธจึงโผล่บ่อยขึ้น
regex เหลือเป็นทางสำรองตอนไม่ได้คีย์นี้กลับมาเท่านั้น · `BRAND WORLD` (คำบรรยายลายตู้) ก็ส่งเฉพาะใบที่มีตู้แล้ว

⚠️ แนบรูปแล้วไม่ได้แปลว่าจบ — รูปบอกได้แค่ **ฮาร์ดแวร์หน้าตายังไง**
บอกไม่ได้ว่า **ของข้างในควรหลากหลาย** ต้องเขียนเป็นคำสั่งเพิ่ม (ดูกฎข้อสาม)

## วิธีตรวจภาพที่ AI แก้ให้ ก่อนเอาเข้าระบบ

ให้วางเป็นชื่อใหม่ก่อน **ห้ามทับของเดิม** แล้ววัดด้วย `PIL.ImageChops.difference`

```
เคสแก้เลขในแบนเนอร์: ต่างจากเดิม 274 พิกเซลจาก 902,486 = 0.03%
→ แก้เฉพาะจุดจริง
```

**ถ้าเปอร์เซ็นต์ความต่างเกิน ~25% แปลว่าโมเดลวาดใหม่ทั้งใบ ให้ตีกลับ**

แล้วครอปเทียบทีละจุด (หัวเรื่อง · ไอคอน · แถบล่าง) ยืนยันว่าภาษาไทยไม่เพี้ยน

⚠️ **อย่าลืมไฟล์เวอร์ชันย่อ** — `srcSet` ชี้ไฟล์ `-800.jpg` ให้จอเล็ก
ถ้าเปลี่ยนแต่ตัวเต็ม คนดูจากมือถือจะเห็นของเก่า และไม่มีใครสังเกตเพราะเดสก์ท็อปถูกแล้ว
