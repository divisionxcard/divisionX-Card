# หน้า /marketing — Marketing OS Console

ออกแบบหน้าเดียวบนเว็บ DivisionX สำหรับคุมงานการตลาดออนไลน์ทั้งวงจร
ตามกรอบ 3 ระบบ (คอนเทนต์ / โซเชียล+ขาย / หลังบ้าน+วัดผล)

---

## 1. ข้อสรุปการออกแบบ: หน้านี้ไม่ใช่ Dashboard

ถ้าออกแบบเป็น dashboard (กราฟเยอะ ๆ) จะพลาดจุดสำคัญที่สุดของแนวคิดนี้

> เจ้าของทำงาน 20% · AI ทำ 80% — **20% นั้นคือการ "ตัดสินใจ"** ไม่ใช่การ "ดูตัวเลข"

หน้านี้จึงเป็น **กล่องรออนุมัติ (Approval Inbox)** เป็นหลัก
เปิดมาต้องเห็นทันทีว่า *"วันนี้มีอะไรรอฉันกดอยู่กี่ชิ้น"* แล้วเคลียร์ให้หมดในไม่กี่นาที
ส่วนตัวเลขและกราฟเป็นของรอง อยู่ล่างลงไป

เกณฑ์วัดว่าหน้านี้สำเร็จ: **เปิดวันละ 2 ครั้ง ครั้งละไม่เกิน 5 นาที แล้วปิด**
ถ้าต้องนั่งจ้องนาน แปลว่าออกแบบผิด

## 2. จาก 3 ระบบ → 4 โซนบนหน้าจอ

| ระบบตามกรอบ | โซนบนหน้าจอ | สิ่งที่เจ้าของทำ |
|---|---|---|
| 1. หาไอเดีย + ผลิตคอนเทนต์ | **A · กล่องอนุมัติ** | อ่านร่าง → ✅/✏️/❌ |
| 2. โซเชียล + ปิดการขาย | **B · กล่องข้อความค้าง** | ตอบที่ AI ตอบไม่ได้ |
| 1+2 (สถานะระบบ) | **C · สายพานการผลิต** | แค่ดูว่าติดตรงไหน |
| 3. หลังบ้าน + วัดผล | **D · ตัวเลข** | อ่านสัปดาห์ละครั้ง |

## 4. รายละเอียดแต่ละโซน

### A · กล่องอนุมัติคอนเทนต์

**ข้อมูลเข้า:** [`deploy/tasks/content_suggestions.json`](../../deploy/tasks/content_suggestions.json)
ที่ [`content_suggester.py`](../../deploy/agents/content_suggester.py) สร้างไว้ (มีอยู่แล้ว ✅)

**การ์ดหนึ่งใบต้องมี:**
- ภาพ/วิดีโอตัวอย่าง (ถ้ายังไม่มี ขึ้น placeholder + ปุ่ม "สร้างภาพ")
- แคปชั่นเต็ม แก้ inline ได้เลย ไม่ต้องเปิด modal
- แพลตฟอร์ม + วัน/เวลาที่จะโพสต์ (แก้ได้)
- **`💡 จาก:` เหตุผลที่ AI เสนอชิ้นนี้** ← สำคัญที่สุด
  เช่น *"OP-13 ยอดขาย +32% ใน 7 วัน"* — เจ้าของตัดสินใจได้ใน 2 วินาทีโดยไม่ต้องไปเปิดข้อมูลเอง

**ปุ่ม:** `✅ อนุมัติ` (→ เข้า `content_queue.json` + ตั้งเวลา) · `✏️ แก้แล้วอนุมัติ` · `❌ ทิ้ง` (+ เหตุผลสั้น ๆ)

> **เหตุผลที่ทิ้งสำคัญกว่าที่คิด** — เก็บไว้ป้อนกลับให้ prompt รอบหน้า
> ไม่งั้น AI จะเสนอแบบเดิมที่ถูกทิ้งซ้ำ ๆ ทุกวัน

### B · กล่องข้อความที่ต้องตอบเอง

**หลักการ:** AI ตอบเองได้ก็ตอบไปเลย ที่ขึ้นหน้านี้คือเฉพาะที่มัน**ไม่มั่นใจ**

เกณฑ์ส่งขึ้นมาให้คนตอบ:
- ถามราคา/โปรที่ไม่มีในฐานข้อมูล
- ร้องเรียน / ตู้มีปัญหา / ขอเงินคืน
- ถามสต็อกเจาะจงสาขา (AI ตอบได้ แต่ต้องยืนยันเพราะข้อมูลอาจเก่า)
- คำถามที่ AI ให้ confidence ต่ำ

**การ์ดต้องมี:** ข้อความลูกค้า · ร่างคำตอบของ AI · **ธงเตือนเมื่อร่างอ้างข้อมูลสด**
(เช่น "เหลือ 8 ซอง" ← ต้องเตือนว่าข้อมูล sync มา 3 ชม.แล้ว)

### C · สายพานการผลิต

แถบสถานะสั้น ๆ ไม่ต้องสวย — ตอบคำถามเดียว: *"ระบบยังทำงานอยู่ไหม"*

แต่ละแถวคือ 1 automation: ชื่อ · เวลารันล่าสุด · 🟢 ผ่าน / 🟡 กำลังทำ / 🔴 ล้ม
🔴 กดแล้วเห็น error + ปุ่ม "สั่งรันใหม่"

**ดึงจาก:** GitHub Actions API (มี [`trigger_workflow.py`](../../deploy/agents/trigger_workflow.py) กับ MCP tool `get_sync_status` อยู่แล้ว ✅)

### D · ตัวเลข

**KPI 5 ใบ** (ตาม [[feedback_kpi_card_design]]: ตัวเลขขนาดเท่ากัน · ไม่เกิน 5 ใบ/แถว · icon มุมขวาบน)
รายรับ · ค่าโฆษณา · ROAS · กำไรสุทธิ · การเข้าถึง — ทุกใบมี % เทียบช่วงก่อน

**กราฟหลัก: ยอดขายรายสาขา + หมุดวันที่โพสต์**
นี่คือกราฟที่ตอบคำถามจริงว่า *"โพสต์แล้วยอดขึ้นไหม"* — ดีกว่ากราฟยอดขายเปล่า ๆ

## 5. ⚠️ ความจริงที่ต้องพูดก่อนสร้าง: Attribution ทำไม่ได้ตรง ๆ

กรอบ 3 ระบบเขียนมาสำหรับธุรกิจที่**ปิดการขายออนไลน์** (มี lead → แชท → โอนเงิน)
แต่ DivisionX ขายผ่าน**ตู้ในห้าง** ลูกค้าเดินมาหยอดเอง — ไม่มี lead ไม่มี checkout

**ผลคือ:**

| ส่วนของกรอบ | ใช้กับ DivisionX ได้ไหม |
|---|---|
| หาไอเดีย + ผลิตคอนเทนต์ | ✅ ใช้ได้เต็ม — มี `content_suggester` อยู่แล้ว |
| ตอบคอมเมนต์อัตโนมัติ | ✅ ใช้ได้เต็ม |
| เก็บ Social Voice ลง DB | ✅ ใช้ได้ — เอามาหา SKU ที่คนถามหา |
| **ปิดการขาย 24 ชม. ผ่านแชทบอท** | ❌ **ไม่มีของให้ปิด** — ขายหน้าตู้อย่างเดียว |
| **CRM / Single Customer ID** | ❌ **ไม่มีข้อมูลลูกค้า** — ตู้ไม่เก็บตัวตนผู้ซื้อ |
| **ใบกำกับภาษีอัตโนมัติ** | ⚠️ เกี่ยวกับ [[project_kingpower_aot]] (ตู้สนามบิน) ไม่ใช่งานการตลาด |
| ROAS / กำไรสุทธิ | ⚠️ **ทำได้แบบประมาณ** — อ่านต่อข้างล่าง |

### ทางออกเรื่อง ROAS: วัดที่ระดับสาขา ไม่ใช่ระดับคน

ยิงแอดแล้วโยงไม่ได้ว่าใครเดินไปหยอดตู้ — แต่**เทียบยอดสาขาก่อน/หลังยิงได้**

```
ยิงแอด targeting รัศมี 5 กม. รอบเซ็นทรัลชลบุรี (chukes04)
  → ดูยอด chukes04 ช่วงยิง เทียบกับ baseline 14 วันก่อนหน้า
  → เทียบกับสาขาอื่นที่ไม่ได้ยิงในช่วงเดียวกัน (control group)
  → ส่วนต่างที่เกินกว่าสาขา control = ผลจากแอด (โดยประมาณ)
```

**มีข้อมูลพร้อมแล้วทุกอย่าง** — ยอดขายรายตู้รายวันอยู่ใน `sales` table
ขาดแค่ค่าโฆษณาจาก Meta ซึ่งดึงผ่าน Meta MCP ได้

> ต้องเข้าใจตรงกันว่านี่คือ **การประมาณ ไม่ใช่ attribution จริง** — วันหยุด/เทศกาล/
> ของเข้าใหม่ ก็ทำให้ยอดขึ้นได้เหมือนกัน จึงต้องมี control group เสมอ

## 7. Data model ที่ต้องเพิ่ม

ย้ายจากไฟล์ JSON ลง Supabase เพราะหน้าเว็บต้องอ่าน/เขียนพร้อมกันหลายที่

```sql
-- ร่างคอนเทนต์ + คิวโพสต์ (แทน content_suggestions.json + content_queue.json)
create table marketing_content (
  id            bigserial primary key,
  status        text not null,        -- draft | pending | approved | scheduled | posted | rejected
  platform      text not null,        -- fb | line | ig | tiktok
  caption       text not null,
  media_url     text,
  media_type    text,                 -- image | video | none
  scheduled_at  timestamptz,
  posted_at     timestamptz,
  source_reason text,                 -- "OP-13 ยอดขาย +32%" ← ที่โชว์เป็น 💡 จาก:
  source_sku    text references skus(sku_id),
  reject_reason text,                 -- ป้อนกลับให้ prompt รอบหน้า
  created_by    text not null,        -- ai | human
  created_at    timestamptz default now()
);

-- คอมเมนต์/ข้อความจากโซเชียล
create table social_messages (
  id            bigserial primary key,
  platform      text not null,
  external_id   text not null,        -- id ฝั่ง FB/LINE (กันซ้ำ)
  author_name   text,
  message       text not null,
  ai_draft      text,                 -- ร่างคำตอบของ AI
  ai_confidence numeric,              -- < เกณฑ์ = ส่งให้คนตอบ
  needs_human   boolean default false,
  answered_at   timestamptz,
  answered_by   text,                 -- ai | human
  final_reply   text,
  created_at    timestamptz default now(),
  unique (platform, external_id)
);

-- ค่าโฆษณารายวันรายแคมเปญ (ดึงจาก Meta/Google)
create table ad_spend (
  id            bigserial primary key,
  date          date not null,
  platform      text not null,        -- meta | google
  campaign      text not null,
  target_machine text references machines(machine_id),  -- แคมเปญนี้ยิงให้สาขาไหน
  spend         numeric not null,
  impressions   int,
  clicks        int,
  reach         int,
  created_at    timestamptz default now(),
  unique (date, platform, campaign)
);
```

`target_machine` คือกุญแจของการวัด ROAS ระดับสาขาในข้อ 5 — **ต้องบังคับกรอกทุกแคมเปญ**

## 8. เฟสการสร้าง

| เฟส | ได้อะไร | พึ่งของนอกไหม |
|---|---|---|
| **1 · หน้าเปล่า + โซน A** | อนุมัติคอนเทนต์บนเว็บแทนแก้ JSON มือ | ❌ ใช้ของที่มีล้วน |
| **2 · โซน C + D (ไม่มี ROAS)** | เห็นสถานะระบบ + ยอดขาย/คอนเทนต์ที่เวิร์ค | ❌ ใช้ของที่มีล้วน |
| **3 · โซน B** | ตอบคอมเมนต์กึ่งอัตโนมัติ | ✅ Meta permission |
| **4 · ROAS เต็ม** | ค่าแอด + กำไรสุทธิ + control group | ✅ Meta MCP |
| **5 · เจนภาพ/วิดีโอ** | ร่างมาพร้อมภาพ ไม่ต้องทำเอง | ✅ API เจนภาพ |

**แนะนำเริ่มที่เฟส 1+2** — ใช้ของที่มีอยู่แล้วทั้งหมด ไม่ต้องรอ approval จากใคร
และได้ของที่ใช้จริงทุกวันตั้งแต่วันแรก

เฟส 3–5 ควรทำทีละอัน หลังจากเฟส 1+2 ใช้ไปสักพักแล้วรู้ว่าจริง ๆ ติดตรงไหน
