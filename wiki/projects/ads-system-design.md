# ออกแบบระบบยิงแอดอัตโนมัติ — สถาปัตยกรรมและเหตุผล

ต่อจาก [[ads-automation-blueprint]] (แผนระดับธุรกิจ) · ไฟล์นี้คือ **การออกแบบระบบ**

วิธีได้มา: ให้ 4 แบบที่ตั้งต้นจากคนละสมมติฐานแข่งกัน → กรรมการ 3 มุมให้คะแนน →
สังเคราะห์แบบที่ชนะ + ต่อของดีจากแบบที่แพ้ → 5 มุมโจมตีหาจุดตาย
(18 เอเจนต์ · เก็บกับดักจากโค้ดเดิม 93 ข้อ · เจอจุดตาย 52 ข้อ critical 16)

## ผลการแข่ง

| แบบ | คะแนนรวม |
|---|---|
| **Brake-First Ads — สร้างเบรกให้เสร็จก่อนต่อคันเร่ง** | **23.5** ← ชนะ |
| แท่นทดลองยิงแอด (measurement-first) | 21 |
| เบรกก่อนคันเร่ง (minimal-surface) | 21 |
| DVX Ads Core — แกนกลาง + adapter ต่อแพลตฟอร์ม | 11 |

**adapter-first แพ้ขาด** — กรรมการทั้งสามมองตรงกันว่าสร้าง abstraction ให้แพลตฟอร์มที่สาม
ที่ยังไม่มีอยู่ ในขณะที่ยังไม่รู้ด้วยซ้ำว่าแพลตฟอร์มแรกคุ้มไหม คือการจ่ายค่าความยืดหยุ่นล่วงหน้า
ด้วยเงินที่ยังไม่มี

## หลักที่ยึด — แยกคำสั่งตามความเสียหายเมื่อทำเกิน

ไม่ได้แยกตาม "อ่าน/เขียน" หรือ "auto/manual" แต่แยกตาม **ถ้าทำซ้ำเกินจำเป็นแล้วเจ็บแค่ไหน**

| ชนิดคำสั่ง | เสียหายเมื่อทำเกิน | เลยออกแบบให้ |
|---|---|---|
| **หยุด** (pause) | ไม่เสียอะไร ทำซ้ำได้ | วิ่งบ่อยที่สุด · เกาะ hook ท้าย stock sync + cron 30 นาที 24 ชม. |
| **เปิด/เพิ่มงบ** | เสียเงินจริงทันที | ผ่านด่านกลางไฟล์เดียว · เฟส 1 ให้คนทำมือ |
| **อ่าน** | ไม่เสียอะไร | ครอบทั้งบัญชี ไม่ใช่แค่ของเรา |

⚠️ **ตัวหยุดห้ามพึ่ง GitHub cron** — repo นี้วัดเองแล้วว่า cron เลื่อน **เฉลี่ย 234 นาที
สาย 100% ของรอบ** (52 รอบ ไม่ตรงเลยสักรอบ) ฝั่ง WW เคยเลื่อน 6 ชม.
เบรกที่มาช้า 4 ชม. = ยอมจ่ายเงินพาคนไปเจอตู้ว่างครึ่งวัน

⚠️ **สายจูงฝั่งแพลตฟอร์ม** — ทุก ad set ตั้ง `end_time ≤ now+48 ชม.` แล้วต่ออายุเป็นรอบ
ถ้าโค้ดเราตายสนิททุกส่วน **แอดดับเองภายใน 48 ชม.** โดยไม่ต้องมีใครทำอะไร

## สถาปัตยกรรม

```
คอนเทนต์เดิม ──post_id──▶ ad_flights (ใบยิง)
                              │
        ┌─────────────────────┼─────────────────────┐
        ▼                     ▼                     ▼
   ตัวหยุด (guard)      เครื่องอ่าน (collect)   ตัววัด (effect)
   hook ท้าย stock sync  cron ราย ชม.          cron 23:00 น.
   + cron 30 นาที        ครอบทั้งบัญชี          อ่าน sales
        │                     │                     │
        └──────▶ adGate.js ◀──┘                     ▼
              (ด่านกลางไฟล์เดียว)           ad_experiment_days
```

**ตัวยิงห้ามรู้จักวิธีวัด · ตัววัดห้ามรู้จักวิธียิง** — สี่สายวิ่งขนานกันและไม่รู้จักกัน

### ตารางที่สำคัญที่สุด 4 ตัว

- **`ad_assignments`** grain = (การทดลอง × ตู้ × **วันไทย**) ตรงเป๊ะกับ `sales` group by
  เก็บ `planned` (ตั้งใจ) แยกจาก `status_actual` (เกิดจริง) — วันที่แอดถูกหยุดกลางวัน
  ต้องไม่ถูกนับเป็นวัน treatment เต็ม
- **`ad_insights`** สแนปช็อต **append-only ห้าม upsert ทับ** (แพลตฟอร์มแก้ตัวเลขย้อนหลัง)
  ⚠️ กฎการอ่าน: หยิบแถวล่าสุดของแต่ละ `(ad_id, stat_date)` — **SUM ทุกแถวได้เงินเกิน ~24 เท่า**
- **`ad_spend_recon`** invariant `account_spend − attributed = 0` ทุกวัน · ไม่เป็น 0 → Telegram
- **`ad_guard_events`** บันทึกทุกการตัดสิน **รวม noop และ heartbeat** — แยก "เงียบเพราะไม่มีเรื่อง"
  ออกจาก "เงียบเพราะพัง"

**schema จงใจไม่มีคอลัมน์ `roas`/`revenue`** พร้อม COMMENT อธิบายว่าทำไม —
เงินสองก้อนอยู่คนละตาราง ผูกกันได้เฉพาะระดับการทดลอง ไม่ใช่ระดับ ad

## จุดตายที่ต้องอุดก่อนเขียนโค้ด (critical 16 · ยกมา 8 ข้อที่เปลี่ยนแผน)

### 1. งบทดลองกับ MDE ขัดกันเอง — ข้อที่ล้มโครงการได้ทั้งโครงการ

```
฿9,000/เดือน ÷ 6 ตู้ ÷ 30 วัน   = ฿50/ตู้/วัน
MDE +20% ของ ฿2,888/ตู้/วัน     = ต้องเพิ่มยอด ฿578/ตู้/วัน
                                → ROAS ที่ต้องเป็นจริง ≈ 11.6 เท่า
```

**แอดสร้างการรับรู้ที่ให้ผล 11 เท่าไม่มีอยู่จริง** แปลว่าการทดลองที่งบเท่านี้
ถูกออกแบบมาให้ได้ผลลัพธ์ "ไม่พบความต่าง" ตั้งแต่ก่อนเริ่ม แล้วเราจะสรุปผิดว่า "แอดไม่ได้ผล"
ทั้งที่จริงคือ "งบไม่พอจะทำให้เกิดผลที่เราตั้งใจจะวัด"

**แก้:** งบกับ MDE ต้องตกลงกันก่อนเริ่ม — ทางเลือกคือเพิ่มงบเป็น ~฿200–580/ตู้/วัน
(≈ ฿36,000–104,000/เดือน สำหรับ 6 ตู้) **หรือ** ลดจำนวนตู้ treatment ให้งบต่อตู้หนาขึ้น
**หรือ** เปลี่ยนคำถามเป็น "ครีเอทีฟแบบไหนคนหยุดดู" ซึ่งงบ ฿9,000 ตอบได้จริง

> ⚠️ ตัวเลข ฿9,000 ในเอกสารแผนเมื่อวานจึงใช้ได้เฉพาะเป็น **งบเรียนรู้ครีเอทีฟ**
> ไม่ใช่งบพิสูจน์ยอดขาย — ต้องแก้เอกสารนั้นด้วย

### 2. เบรกที่ทำงานถูกต้อง ทำให้ผลการทดลองต่ำกว่าจริง

วันที่แอดได้ผลดีที่สุด = วันที่ตู้ขายจนของร่อยหรอ → guard สั่ง pause เพราะ fill_ratio < 25%
→ ตัววัดตัดตู้-วันนั้นออก (`status_actual ≠ 'on'`) **ยิ่งแอดได้ผล ยิ่งถูกตัดออก**

**แก้:** แยก "หยุดเพราะของหมด" ออกจาก "หยุดเพราะระบบมีปัญหา" · เคสแรกต้องนับเป็น
วัน treatment ที่มีผลจริง (censored at the top) ไม่ใช่ตัดทิ้ง

### 3. ข้อความแจ้งเตือนปนเปื้อนการทดลองเอง

`alert_ad_paused_stock()` บอกว่า "หยุดใบ DVX-F03 เพราะ chukes01 ของใกล้หมด"
→ แอดมินเห็นแล้วไปเติมตู้นั้นก่อนตู้อื่น → ตู้ treatment ได้รับการดูแลดีกว่าตู้ควบคุม
**ผลที่วัดได้จึงไม่ใช่ผลของแอด แต่เป็นผลของการเติมของ**

**แก้:** ช่วงทดลอง ข้อความเตือนห้ามระบุว่าตู้ไหนอยู่ arm ไหน · หรือส่งข้อมูลสต็อก
ของตู้คู่กันไปพร้อมกันเสมอ

### 4. ตู้ควบคุมถูกลบทั้งแขนด้วยตัวกรองบรรทัดเดียว

controlFlow เขียนว่า "ตัดตู้-วันที่ `status_actual ≠ 'on'` ออก" แต่ตู้ฝั่ง control
ถูก generate มาด้วย `planned = off` และ `status_actual = off` เสมอ → **ตัวกรองลบกลุ่มควบคุมทิ้งทั้งหมด**

**แก้:** เงื่อนไขต้องเป็น "`status_actual ≠ planned`" ไม่ใช่เทียบกับ `'on'`

### 5. แอดที่ดูเหมือนวิ่งอยู่แต่ถูกแพลตฟอร์มปิดไปแล้ว

ครีเอทีฟถูก Meta ปฏิเสธ → ad set ยัง `ACTIVE` แต่ `effective_status = DISAPPROVED`
ระบบเราเห็นว่า "วิ่งอยู่" ตู้นั้นถูกนับเป็นวัน treatment ทั้งที่ไม่มีใครเห็นแอดเลย

**แก้:** guard ต้องอ่าน `effective_status` ไม่ใช่ `status` · และ `ad_assignments.status_actual`
ต้องมาจาก effective_status ของจริง

### 6. ช่วงมืดกลางคืน

hook ท้าย stock sync รอบสุดท้ายวิ่ง ~00:15 น. รอบถัดไป 09:10 น. (ซึ่งจริง ๆ มา 10:xx–15:xx)
→ **ช่องว่าง ~10 ชม. ที่งบทะลุแล้วไม่มีใครหยุด**

**แก้:** cron 30 นาทีตลอด 24 ชม. เป็นตาข่ายชั้นสอง (ยอมรับว่ามันสาย แต่ดีกว่าไม่มี)
+ `end_time ≤ 48 ชม.` เป็นชั้นสุดท้ายที่ไม่พึ่งโค้ดเราเลย

### 7. เพดานงบที่ไม่เคยถูกแตะ

ตั้งเพดาน ฿1,000/วัน แล้วยิงจริง ฿900/วัน → ไม่เคยมี alert สักครั้ง
แต่ 45 วัน = ฿40,500 ซึ่งเกินงบทั้งโครงการไปแล้ว

**แก้:** เพดานต้องมีทั้ง **รายวัน** และ **ยอดสะสมต่อการทดลอง** · และ env ที่หายไป
ต้อง fail-closed (`ADS_HARD_DAILY_CAP_THB` ไม่มี = ปฏิเสธการยิง ไม่ใช่ `NaN` แล้วผ่าน)

### 8. บูสต์โพสต์ที่ AI แต่งตัวเลขขึ้นเอง

โพสต์ที่เอนเกจดีที่สุดในคิวคือชิ้นที่เขียนว่า "ยอดขายพุ่ง 61% ตั้งแต่ OP-16 เข้าตู้"
และโปสเตอร์มีข้อความ "การ์ดใบนี้เคยขายได้ 15,000" — ทั้งคู่โมเดลแต่งขึ้นเอง

**แก้:** ด่านก่อนบูสต์ต้องเข้มกว่าด่านก่อนโพสต์ — โพสต์ธรรมดาผิดแล้วลบได้
แต่แอดคือการ**ซื้อสื่อ**เพื่อกระจายคำกล่าวอ้างนั้น · ต้องมีด่านตรวจตัวเลขในแคปชั่น
ว่าอ้างอิงข้อมูลจริงใน DB ได้ไหม ก่อนอนุญาตให้ boost

## ลำดับการสร้าง

**เฟส 1 (6 วัน) — เบรก + เครื่องอ่าน + คนสร้างแคมเปญมือ**
สร้างทุกอย่างยกเว้นตัวยิง · คนเปิด Ads Manager ตั้ง ad set เอง (~10 นาที/ใบ)
ตั้งชื่อขึ้นต้น `DVX-F<n>` · `end_time = now+48h` · ปลายทาง `/go/DVX-F03?m=chukes01`

**เงื่อนไขจบเฟส 1 — ทดสอบเบรกด้วยเงินจริง ฿1:**
1. ตั้ง `daily_cap_thb = 0` → guard ต้อง PAUSE จริง **ดูใน Ads Manager ว่าหยุดจริง ไม่ใช่ดูแค่ HTTP 200**
2. ปลอม `machine_stock` ให้ตู้หนึ่งของหมด → ต้องหยุดภายในรอบ sync ถัดไป
3. ถอด token → ต้องขึ้นแดง + Telegram ไม่ใช่ข้ามเงียบ

**เฟส 2 (+5 วัน) — มอบสิทธิ์สร้างแคมเปญให้โค้ด** เฉพาะเมื่อเฟส 1 ผ่านครบ
