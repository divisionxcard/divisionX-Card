# เงินของบิล VMS เข้าผิด SKU มาตั้งแต่ พ.ค. — ยอดรวมถูก แต่รายตัวผิด

เจ้าของเทียบหน้าเว็บกับหลังบ้าน VMS วันที่ 30 ส.ค. ที่ chukes02 แล้วเจอว่า
**One Piece OP-17 ของเราขึ้น ฿1,196.67 แต่ VMS บอก ฿1,250**

## อย่างแรกที่ต้องสังเกต — ยอดรวมตรงกันเป๊ะ

ทั้งสองฝั่งรวมได้ **฿4,640** เท่ากัน จำนวนซองก็ตรง (20 ซอง)
แปลว่า**ไม่ใช่ข้อมูลหาย** ปัญหาอยู่ที่ "เงินก้อนเดียวกันถูกแบ่งเข้า SKU คนละแบบ"

> ถ้าดูแค่ยอดรวมรายวันจะไม่มีวันเจอ — และที่ผ่านมาเราตรวจกันแค่ยอดรวมมาตลอด

## ต้นตอ: บิลใบเดียวที่ซื้อหลายอย่าง

```
บิล 14:28:27 · รวม 590 บาท
   เราบันทึก   FB 04 196.67 · FB 09 196.67 · OP 17 196.67   ← หารสาม
   VMS จริง    FB 04 110    · FB 09 230    · OP 17 250
```

OP-17 ขายไป 5 ซอง 5 บิล มี **บิลเดียว**ที่ปนของอื่น แล้วโดนเฉลี่ยลงจาก 250 → 196.67
ขาดไป **53.33 บาท** ตรงกับที่เจ้าของเห็นพอดี

`vms_sales_api.py` บรรทัดเดียว:

```python
per_item_price = total_price / n_items      # ถูกเฉพาะตอนของในบิลราคาเท่ากัน
```

VMS schema ใหม่ (rebuild 28 เม.ย. 2026) ส่งมาแค่ `cart_slot` กับยอดรวมของบิล
**ไม่ส่งราคารายชิ้น** ตอนเขียน path นี้จึงไม่มีทางเลือกอื่นนอกจากหารเฉลี่ย

## หาว่าเริ่มพังตอนไหน โดยไม่ต้องเดา

นับบิลที่มีหลาย SKU แล้วดูว่า "ทุกบรรทัดได้เงินเท่ากันเป๊ะ" กี่ %:

```
เม.ย. 2026   642 บิล   23%   ← เดือนที่ VMS เปลี่ยน schema
พ.ค. 2026    862 บิล  100%
มิ.ย. 2026   548 บิล   96%
ก.ค. 2026    383 บิล  100%
ส.ค. 2026    210 บิล  100%
```

ลายเซ็นชัดเจน — เม.ย. เป็นเดือนคาบเกี่ยว จากนั้นเข้า path ใหม่ 100%
(มิ.ย. 96% เพราะบางวันตกไปใช้ตัวอ่าน XLSX ซึ่งมีราคารายบรรทัดจริง)

## ขนาดของผลกระทบ

เดือน ส.ค. เดือนเดียว: **210 จาก 1,281 บิล (16%) · 536 แถว · เงินนั่งผิด SKU ฿18,987**
ผลรวมสุทธิ = 0 (เงินไม่หาย แค่ย้ายที่) และ**ทิศทางคงที่**:

| ถูกบันทึกต่ำกว่าจริง | | ถูกบันทึกสูงกว่าจริง | |
|---|---|---|---|
| OP 13 | +฿2,448 | OP 16 | −฿1,384 |
| PRB 01 | +฿1,720 | PKM Ninja | −฿1,353 |

SKU แพงเสียเปรียบ SKU ถูกได้เปรียบเสมอ — เพราะการหารเฉลี่ยดึงทุกอย่างเข้าหาค่ากลาง

**กระทบหน้า "วิเคราะห์ SKU" โดยตรง** ซึ่งเป็นหน้าที่ใช้ตัดสินใจว่าจะดัน SKU ไหน
เท่ากับเราตัดสินใจการตลาดจากอันดับที่ผิดมา 4 เดือน

เฉพาะ VMS — Payif ใช้ `amount` รายชิ้น · WorldWide ใช้ `dealPrice` รายชิ้น ทั้งคู่ถูกอยู่แล้ว

## ทางแก้ที่เลือก — เก็บราคาต่อช่อง ไม่ใช่ราคากลาง

> *"ขอเป็นระดับ 2 เพื่อต้องการให้ข้อมูลในระบบถูกต้องที่สุด 100% รวมถึงในอนาคตด้วย"*

ราคากลางตัวเดียว (`skus.sell_price`) ทำได้เร็วกว่า แต่**จะสร้างความผิดพลาดใหม่** —
VMS ตั้งราคา**แยกตามตู้และแยกตามช่อง** และราคากลางในตารางค้างเก่าได้จริง
(ตารางบอก OP 08 = 120 แต่ chukes02 ขาย 140)

จึงเก็บ `pay_price` รายช่องลง `machine_stock.sell_price` (migration 071) ตอน sync สต็อก —
endpoint `/slots/` ส่งมาให้อยู่แล้ว ไม่ต้องยิงเพิ่มสักครั้ง

ทางถอย 2 ชั้นเมื่อไม่มีราคาต่อช่อง: **ราคากลาง `skus` → หารเฉลี่ยแบบเดิม**

## รายละเอียดที่ตัดสินใจแล้วมีผลจริง

⚠️ **ราคาไม่ครบทุกบรรทัด = หารเฉลี่ยทั้งบิล** ห้ามถ่วงเฉพาะบรรทัดที่รู้ราคา —
จะเพี้ยนหนักกว่าหารเฉลี่ยเสียอีก เพราะบรรทัดที่ไม่รู้ราคาจะได้ 0

⚠️ **ราคา 0 ไม่นับเป็นราคา** ไม่งั้นบรรทัดนั้นได้เงิน 0 บาททั้งที่ลูกค้าจ่ายจริง

⚠️ **เศษทศนิยมต้องไม่หาย** — ยัดเข้าบรรทัดยอดสูงสุดให้ผลรวมเท่ายอดบิลเป๊ะ
ของเดิมบิล 220 ได้ 219.99 · บิล 590 ได้ 590.01 (เงินหาย/เกินทีละสตางค์ทุกบิล)

⚠️ **ช่องที่ map SKU ไม่ได้ ทิ้งทั้งบรรทัดพร้อมส่วนแบ่งของมัน** ไม่โยนเงินให้บรรทัดอื่น
ไม่งั้น SKU ที่เหลือจะพองเกินจริง

⚠️ **ตัว sync สต็อกต้องไม่ตายถ้ายังไม่ได้รัน migration** — เช็กว่าคอลัมน์มีจริงก่อน
ถ้าไม่มีก็ถอดฟิลด์แล้วเดินต่อ · ปล่อยให้ upsert 400 ทั้งชุด = สต็อกทั้งรอบหายเพราะฟีเจอร์เสริม

## บทเรียน

**"ยอดรวมตรง" ไม่ได้แปลว่า "ข้อมูลถูก"** — ตรวจกันมาหลายเดือนด้วยยอดรวมรายวัน
ซึ่งตรงเป๊ะทุกวัน ทั้งที่ชั้นล่างลงไปผิดมาตลอด ตัวเลขที่ผิดแบบ**ผลรวมเป็นศูนย์**
เป็นชนิดที่ซ่อนตัวได้ดีที่สุด และต้องตรวจที่ระดับที่ละเอียดกว่าจึงจะเจอ

**ปลายทางที่ API ไม่ส่งข้อมูลมาให้ ต้องไปเอามาจากที่อื่น ไม่ใช่เดา** — ตอน VMS
เปลี่ยน schema แล้วเลิกส่งราคารายชิ้น ทางออกที่เลือกตอนนั้นคือหารเฉลี่ย
ซึ่งอ่านแล้วเหมือนสมเหตุสมผล แต่แปลว่าตัวเลขทุกตัวหลังจากนั้นเป็นค่าประมาณโดยไม่มีใครรู้
ราคาที่ต้องใช้อยู่ในมือมาตลอด — endpoint สต็อกที่เรายิงทุกวันส่ง `pay_price` มาให้ด้วยซ้ำ
