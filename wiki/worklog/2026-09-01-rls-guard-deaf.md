# ตัวเฝ้า RLS ดังไม่ได้มา 7 รอบ เพราะไม่มีใครใส่กุญแจให้มัน

งานนี้ไม่ได้ตั้งใจทำ — โผล่มาจากการรัน `rls_check.py` เพื่อ**ยืนยัน migration 073**
ที่เพิ่งสร้างตาราง `refill_plans` ตามขั้นตอนปกติ

```
ai_credit_readings   🔴 อ่านได้ · ลบได้     ← migration 070 (28 ส.ค.)
refill_plans         🔴 อ่านได้ · ลบได้     ← migration 073 (เมื่อวาน)
```

## รูแรก: ลอกแม่แบบมาไม่ครบ

migration 069 กันคนนอกด้วย **สองชั้น** — `ENABLE ROW LEVEL SECURITY` และ
`REVOKE ALL ON <table> FROM anon` · migration 070 ลอกมาแต่ชั้นแรก และผมลอก 070 มาอีกที
ตอนเขียน 073 เลยได้รูเดียวกันติดมาด้วย

⚠️ **RLS อย่างเดียวไม่พอ** — RLS + ไม่มี policy สำหรับ anon ทำให้ SELECT คืน
**200 ว่าง ๆ ไม่ใช่ error** และ DELETE คืน 204 ข้อมูลยังไม่รั่วก็จริง
แต่เหลือด่านชั้นเดียว วันไหนมีคนสร้าง policy กว้างไปหรือ RLS ถูกปิด = เปิดโล่งทันที
ส่วน REVOKE ตัดตั้งแต่ระดับ GRANT ตอบ 401/403 ไปเลย

> กฎข้อนี้**เขียนไว้ในความจำถาวรอยู่แล้ว** ตั้งแต่ 26 ส.ค. ("ต้องมี RLS + policy + REVOKE
> ในไฟล์เดียวกัน") แต่ยังถูกลืมสองครั้งใน 4 วัน — กฎที่เขียนไว้ไม่ได้แปลว่ากฎที่ถูกทำตาม
> สิ่งที่จับได้จริงคือ**ตัวตรวจที่รันทุกครั้ง** ไม่ใช่เอกสาร

## รูที่สอง (ใหญ่กว่า): ตัวเฝ้ามีอยู่ แต่ตาบอดมาตั้งแต่วันแรก

`rls-guard.yml` ตั้งไว้ดีมาก — รันทุกจันทร์ + ทุก push ที่แตะ `migrations/**`
มันควรจับ `ai_credit_readings` ได้ตั้งแต่วันที่ 070 ขึ้น แล้วทำไมไม่มีใครรู้?

ดึงประวัติจริงจาก GitHub API:

```
รันไป 7 รอบตั้งแต่ 26 ส.ค. · แดงทุกรอบ · ขั้นแจ้งเตือน "skipped" ทุกรอบ
```

**ไม่เคยตั้ง secret `SUPABASE_ANON_KEY` ใน GitHub** → สคริปต์ออก `code=2` (ตรวจไม่ได้)
ซึ่งเงื่อนไขเดิมเตือนเฉพาะ `code=1` (รั่วจริง)

เจตนาเดิมถูกต้อง — *"ขาด secret ไม่ใช่ช่องโหว่ อย่าเตือนหลอก"* — แต่ผลลัพธ์จริงคือ
**ตัวเฝ้าไม่เคยตรวจอะไรเลยสักครั้ง และไม่เคยบอกใครว่ามันตรวจไม่ได้**
เหลือแค่กากบาทแดงใน Actions ที่ไม่มีใครเปิดดู

ราคาที่จ่ายไปแล้ว: `ai_credit_readings` เปิดให้ anon อ่าน/ลบได้ค้าง **4 วันเต็ม**
ทั้งที่ตัวเฝ้ารันตอน push migration นั้นพอดี

## แก้อะไรไป

1. **migration 074** — REVOKE ทั้งสองตาราง + ไล่ปิดทุกตารางใน `public` ที่ anon
   ยังมีสิทธิ์ (idempotent) พร้อมแม่แบบ 3 บรรทัดไว้ในหัวไฟล์
2. **`rls-guard.yml` เตือนทั้ง `code=1` และ `code=2`** แยกข้อความคนละแบบ
   *ตัวเฝ้าที่ดังแล้วไม่มีคนได้ยิน = ไม่มีตัวเฝ้า · ยอมเตือนหลอกดีกว่าเงียบตอนรั่วจริง*
3. แก้ `grep '^🔴'` → `'🔴'` — บรรทัดในตารางมี 🔴 อยู่กลางบรรทัด ไม่ใช่คอลัมน์แรก
   ของเดิมต่อให้ดังก็จะส่งข้อความที่มีสรุปว่างเปล่า (บั๊กซ้อนบั๊ก ไม่มีใครเคยเห็นเพราะไม่เคยดัง)
4. ตั้ง secret `SUPABASE_ANON_KEY` ให้ผ่าน API (เข้ารหัสด้วย libsodium sealed box)
   ⚠️ สคริปต์เทียบก่อนส่งว่าไม่ใช่ service key — ถ้าหยิบผิดตัวนั้น ตัวเฝ้าจะรายงานว่า
   "ปลอดภัย" ทุกครั้งตลอดไปทั้งที่รั่วอยู่ ซึ่งแย่กว่าไม่มีตัวเฝ้า

## ทดสอบท่อแจ้งเตือนจริง โดยไม่แตะฐานข้อมูล

ตอนแรกเสนอว่าจะสร้างตารางทดสอบที่จงใจไม่ REVOKE — **แล้วพบว่าตัวเองทำไม่ได้**
`CREATE TABLE` เป็น DDL ซึ่ง PostgREST รันไม่ได้ ต้องเข้า SQL Editor เท่านั้น

วิธีที่ใช้แทน: **ลบ secret ออกชั่วคราว** → ตัวเฝ้าได้ `code=2` ซึ่งเป็นสาขาที่เพิ่งเขียน
และไม่เคยรันเลย → ยิง → ใส่ secret กลับ (ห่อด้วย `try/finally` ให้คืนค่าได้เสมอ)

```
รอบทดสอบ    แจ้งเตือน success  ← เจ้าของยืนยันว่าข้อความเข้าแชทส่วนตัวจริง
รอบยืนยัน    แจ้งเตือน skipped · job เขียว
```

เลือกทดสอบสาขา `code=2` เพราะใช้ท่อส่งเดียวกับ `code=1` ทุกบรรทัด ต่างแค่ข้อความ —
ครอบคลุมทั้งคู่โดยไม่ต้องทำให้ฐานข้อมูลรั่วจริงเพื่อทดสอบ

## บทเรียน

**ตัวเฝ้าที่ไม่เคยถูกทดสอบ คือความมั่นใจปลอม ๆ ที่แพงกว่าไม่มีเลย** — 6 วันที่ผ่านมา
ทุกคนเชื่อว่ามีตัวเฝ้าคอยดูอยู่ ทั้งที่มันตาบอดตั้งแต่วันแรก ความเชื่อนั้นเองที่ทำให้
ไม่มีใครไปตรวจด้วยมือ

**เส้นแบ่งระหว่าง "ไม่มีปัญหา" กับ "ตรวจไม่ได้" ต้องดังทั้งคู่** — ตอนออกแบบมันดูสมเหตุสมผล
ที่จะเงียบเมื่อ "ตรวจไม่ได้" เพราะไม่ใช่ช่องโหว่ แต่สถานะนั้นแหละที่กินเวลา 7 รอบ
โดยไม่มีใครรู้ · สถานะที่ไม่รู้ผล ต้องเสียงดังพอ ๆ กับสถานะที่รู้ว่าแย่

**งานตรวจที่ทำตามขั้นตอนธรรมดา คือสิ่งที่เจอของ** — ไม่มีใครสั่งให้หาช่องโหว่วันนี้
มันโผล่มาจากการรัน `rls_check.py` เพื่อยืนยัน migration ของตัวเองตามปกติ
ขั้นตอนที่ "รู้สึกว่าไม่จำเป็น" มักเป็นขั้นตอนที่จ่ายคืนมากที่สุด
