แต่เป็น**เลขที่หมดอายุไปแล้ว** (`purge_after_days: 5` กวาดของเก่าทิ้งไปตั้งแต่นั้น)

| | Hermes ว่า | ของจริง 31 ส.ค. |

| คิว `status=new` | 107 ชิ้น | **35 ชิ้น** |

**ทิศทางยืนยันได้** จากอัตราถูกหยิบไปใช้จริง:

```

news      14 ชิ้น → ใช้จริง  8 (57%)
```

แหล่งที่เติมของมากที่สุดคือแหล่งที่ถูกใช้น้อยที่สุด คิวที่เต็มไปด้วยของหน้าตาเดียวกัน
ทำให้คนเลิกกวาดสายตา แล้วของดีที่ปนอยู่ก็จมไปด้วย

## ด่านอยู่ที่ save() ไม่ใช่ที่ตัวเก็บแต่ละแหล่ง

คีย์เป็น `(source, subtype)` เพราะ **subtype คือตัวแทนของ "มุม" ที่แท้จริง** —
`angle` ของสัญญาณภายในเป็นข้อความตายตัวต่อ subtype (`machine_drop` 8 ชิ้นใช้ประโยค
เดียวกันเป๊ะ) ส่วน `falling_sku` ข้อความต่างกันเพราะแทรกชื่อ SKU
แต่เป็นคอนเทนต์ชนิดเดียวกันทั้งก้อน — ถ้าเทียบที่ตัวอักษรจะจับตัวที่หนักที่สุดไม่ได้เลย

สามข้อที่ตัดสินใจแล้วมีผลจริง:

**นับของที่ค้างในคิวรวมด้วย ไม่ใช่นับแค่ในรอบนี้** — ถ้านับแค่รอบเดียว เก็บวันละ 5
สิบวันก็ได้ 50 ชิ้นเหมือนเดิม ซึ่งคือรูปของปัญหาที่เกิดจริง `mdrop`/`fall`
ใช้กุญแจกันซ้ำรายสัปดาห์ ตู้/SKU เดิมจึงกลับเข้าคิวได้ทุกสัปดาห์โดยไม่ชนกุญแจเก่า

**ตัดจากตัวคะแนนต่ำ ไม่ใช่ตัดท้ายตามลำดับที่เก็บมา** — โควตาที่เหลือควรตกกับสัญญาณ
ที่แรงที่สุดของกลุ่มนั้น

**ข้ามแล้วต้องบอก** — log บอกจำนวน กลุ่มที่โดน และคิวเดิมของกลุ่มนั้น
(บทเรียน *"สำเร็จแล้วเงียบอ่านไม่ต่างจากล้มเหลวแล้วเงียบ"* จาก [[2026-08-28-review-of-yesterday]])

ของที่ท่วมอยู่ก่อนแล้วไม่ได้ลบ — `purge_after_days: 5` ทยอยเก็บกวาดให้เอง
ด่านนี้กันของใหม่ไม่ให้ไหลเข้ามาเติมซ้ำเท่านั้น

# แล้วก็พบว่าตัวแก้ "ที่ราก" ไม่เคยได้ทำงาน

ด่านข้างบนเป็นการแก้ที่ปลายทาง ของที่แก้ที่รากจริง ๆ คือ `idea_angles.py`
ที่ให้ AI คิดมุมเล่า 3 มุมต่อไอเดีย แทน template ตายตัว 7 แบบ (ทำไว้ 10 ส.ค.)

เลยไปนับดูว่ามันทำงานได้ผลแค่ไหน:

```
marketing_ideas 60 แถว → มี angles  5 แถว (8%)
คิว status=new  35 ชิ้น → มี angles  0 ชิ้น
```

**ไม่มีสักชิ้นในคิวที่ได้มุมจาก AI** ทุกชิ้นยังใช้ template เดิม

## ยิงของจริงแล้วเจอต้นเหตุในนาทีเดียว

```
HTTP 503 "This model is currently experiencing high demand"
```

`ask_gemini` รับมือแค่ 429 · code อื่น `raise` ออกไปหมด → `main` จับแล้วนับเป็น
"ชิ้นนี้ล้มเหลว" แล้วเดินต่อ · workflow ตั้ง `continue-on-error: true` ไว้
(ถูกแล้วสำหรับเรื่องโควตา) **ผลรวมคือล้มทุกชิ้นโดยไม่มีใครรู้ ไฟเขียวทุกเช้า**

ที่แสบคือฝั่งเว็บแก้เรื่องนี้ไปแล้วตั้งแต่ 17 ส.ค. (`5742d50` · `lib/geminiText.js`
แยกความล้มเหลวเป็น 4 แบบ) และ**คอมมิทนั้นแตะไฟล์นี้อยู่แล้ว** (ตัดชื่อโมเดลที่ตายออก)
แต่ตรรกะลองซ้ำไม่ได้ตามมาด้วย

> ท่อสองเส้นยิงปลายทางเดียวกัน แก้แค่เส้นเดียว — และเส้นที่ลืมคือเส้นที่ไม่มีคนดู
> เพราะมันรันตอนตีเจ็ดแล้วไม่มีใครเปิด log

## แยกให้ตรงชนิด ไม่งั้นแก้ผิดทาง

| อาการ | ทางแก้ |
|---|---|
| 503/500/502 · high demand | ล้นชั่วคราว → รอ 1.5 แล้ว 3 วิ ค่อยเปลี่ยนรุ่น |
| 429 PerDay | โควตาหมด → เปลี่ยนรุ่นทันที (โควตานับแยกตามรุ่น) |
| 429 อื่น | ยิงถี่ไป → รอ 20/45/90 วิ |
| 404 · no longer available | รุ่นตาย → เปลี่ยนรุ่นถาวร |
| MAX_TOKENS แต่ไม่มีข้อความ | คิดจนหมดโควตา → ไปรุ่น lite ที่คิดน้อยกว่า |

⚠️ **`Router` เดิมจำ "โมเดลที่ล้ม" ทุกชนิดว่าหมดถาวร** — 503 ครั้งเดียว ซึ่งเป็นอาการ
ที่หายเองใน 2-3 วินาที จึงปลดโมเดลตัวดีทิ้งไปทั้งรอบ 40 ชิ้น
แยกเป็น `permanent` / ชั่วคราวแล้ว: ชั่วคราว = ข้ามไปตัวถัดไปเฉพาะชิ้นนี้
ชิ้นหน้ากลับมาเริ่มที่รุ่นหลักเหมือนเดิม

⚠️ **ล้มชั่วคราวครบทุกรุ่นต้องไม่ถอยไป Ollama** — Ollama ไม่มีบน GitHub Actions
ถอยไปแล้วต่อไม่ติด `main` จะ `break` ทิ้งทั้งรอบ ทั้งที่ Gemini แค่สะอึก

เก็บเพิ่มระหว่างทดสอบ: **socket timeout เป็นคนละชนิด exception กับ 503**
(`TimeoutError` ไม่ใช่ `HTTPError`) จึงลอดตารางข้างบนไปได้ ทั้งที่เป็นอาการชั่วคราว
เหมือนกัน — เจอสด ๆ ตอนยิงทดสอบ ชิ้นแรกได้ *"read operation timed out"*
ให้โอกาสยิงใหม่ครั้งเดียว ไม่ใช่ชุดเต็ม เพราะแต่ละครั้งกินได้ถึง 90 วิ และทั้ง job มี 10 นาที

## บทเรียน

**ตัวเลขจาก Hermes ต้องตรวจทุกครั้ง แต่ทิศทางมันมักถูก** — รอบนี้ผิดทุกตัวเพราะอ้าง
ของที่ถูก purge ไปแล้ว ถ้าเชื่อเลยจะไปตั้งด่านผิดตัว ถ้าไม่ฟังเลยก็จะไม่เห็นปัญหา
วิธีใช้คือ **เอาข้อสังเกตมา แล้ววัดเอง**

**งานที่ไม่มีใครดูผลลัพธ์ = งานที่พังได้เงียบที่สุด** — `continue-on-error` ทำให้
job เขียวทุกเช้ามา 3 สัปดาห์ ทั้งที่ผลิตของได้ 8% ตัวชี้วัดที่จับได้ไม่ใช่สถานะ job
แต่คือ **"ของที่ควรมี มีอยู่กี่แถวใน DB"**

**แก้ที่ปลายทางแล้วต้องกลับไปดูว่าต้นทางยังเดินอยู่ไหม** — ตั้งใจมาทำด่านกันมุมซ้ำ
ซึ่งเป็นการแก้ปลายทาง แล้วบังเอิญไปเจอว่าตัวแก้ต้นทางที่ทำไว้เมื่อสามสัปดาห์ก่อนตายสนิท
ถ้าไม่ได้นับ `angles` ในคิวก็คงไม่รู้ และคงคิดว่าด่านใหม่คือทางแก้ทั้งหมด
