# pf01 แสดงตัวเลขสต็อกเก่าเดือนกว่า เพราะ scraper ไม่เคยลบช่องที่หายไป

เจอระหว่างจะส่งรายงานการเปลี่ยนสินค้าย้อนหลังให้แอดมิน ([[2026-08-19-slot-swap-alerts-missing]])
พบว่า pf01 ขึ้น "Yu-Gi-Oh Chaos Origins ถูกถอดออก" **วันละ 3-4 ครั้ง ทุกวัน ตั้งแต่ 15 ก.ค.**
เหลือ 12 เท่ากันเป๊ะทุกครั้ง — ของจริงไม่มีใครถอดสินค้าตัวเดิมวันละ 3 รอบติดกัน 35 วัน

**ถ้าส่งรายงานไปตามที่ตั้งใจ แอดมินจะโดนถล่ม 36 รายการปลอม แล้วเลิกเชื่อการแจ้งเตือนตั้งแต่ครั้งแรก**

## ไล่ทีละชั้น

**ชั้น 1 — ของยังอยู่จริงไหม** `machine_stock` บอกว่า Chaos Origins อยู่ช่อง 060 เหลือ 12
ไม่ได้หายไปไหน แต่ระบบบันทึกว่าถูกถอดออกทุกรอบ **โดยไม่มี `swap_in` คู่กันเลยสักครั้ง**

**ชั้น 2 — เทียบเวลาซิงค์รายช่อง** เจอของจริง:

```
55 ช่อง  ซิงค์ล่าสุด 2026-08-19 12:22   ← ปกติ
 5 ช่อง  ซิงค์ล่าสุด 2026-07-14 18:17   ← ค้างมาเดือนกว่า
         052 Dragon Ball FB-02 · 054 FB-04 · 056 FB-06 · 058 FB-09 · 060 Chaos Origins
```

ทุกช่องที่ค้างเป็น**เลขคู่ 052-060** ชัดเกินกว่าจะบังเอิญ

**ชั้น 3 — โค้ดเราหรือ portal** ไล่ git log ช่วง 12-17 ก.ค. ไม่มีคอมมิตไหนแตะโค้ดสแกนช่องเลย
แล้วเปิด log ของ workflow รอบล่าสุดดู:

```
📦 ดึง pf01 (shop=208)...
  ✅ พบ 55 slots          ← portal ส่งมาแค่ 55
💾 บันทึก 55 slots ลง Supabase...
```

→ **สคริปต์ไม่ได้ดึงมาไม่ครบ · portal เลิกส่ง 5 ช่องนั้นเอง** (น่าจะปรับชั้นวางหรือปิดช่องในระบบ)

## บั๊กจริงฝั่งเรา — คนละเรื่องกับ portal

`save_to_supabase` ใช้ `upsert(on_conflict="machine_id,slot_number")` **ไม่เคยลบ**
ช่องที่หายไปจึงค้างพร้อมตัวเลขวันสุดท้ายที่เห็น **ตลอดไป**

ตรวจแล้วพบว่า **ไม่มี scraper ตัวไหนเลยทั้ง 3 แบรนด์ที่จัดการเรื่องนี้** — เป็นช่องโหว่ร่วม
pf01 แค่เป็นที่แรกที่ช่องหายจริงจนเห็นผล

**ผลกระทบ:** รายงานเตรียมของเติมตู้ของ 5 ช่องนี้เป็นข้อมูลเดือนที่แล้ว
ซึ่งเป็นรายงานที่แอดมินใช้ทุกวัน (ดู [[project_actual_usage_scope]])

## วิธีแก้

โมดูลใหม่ `deploy/scraper/stock_reconcile.py` เรียกจากทั้ง 3 สคริปต์
**วางไว้หลัง `save_to_supabase` เสมอ** — ก่อน save จะยังไม่มีแถวใหม่ให้เทียบ

⚠️ การลบย้อนไม่ได้ จึงมีด่านกันพลาด 3 ชั้น ทดสอบกับข้อมูลจริงครบทุกเคส:

| เคส | ผล |
|---|---|
| pf01 จริง — ได้ 55 จาก 60 | ลบ 5 ✓ |
| API ล่ม คืน 0 ช่อง | ไม่ลบ ✓ |
| API ตอบไม่ครบ คืน 20 จาก 60 (33%) | ไม่ลบ — ต่ำกว่าเกณฑ์ 50% ✓ |
| ตู้ WW ปกติ ส่งครบ | ไม่ลบ ✓ |

(ตัวทดสอบตั้งให้ `delete()` ระเบิดถ้าถูกเรียกตอน dry-run — ไม่ถูกเรียกเลย)

## ล้างของค้างครั้งเดียวด้วยมือ ไม่รอรอบซิงค์

ถ้าปล่อยให้ซิงค์รอบหน้าเจอเอง มันจะบันทึก `swap_out` 5 รายการแล้วส่ง Telegram
บอกแอดมินว่า "เอาของออก 5 รายการ" ทั้งที่ของหายไปตั้งแต่ 14 ก.ค. — ขัดกับรายงาน
ย้อนหลังที่เพิ่งส่งไป (ตั้งใจไม่รวม pf01 เพราะรู้ว่าเป็นบั๊ก)

จึงรัน `reconcile_removed_slots` ด้วยมือ ใช้ตรรกะเดียวกับในสคริปต์ ไม่ได้เขียน SQL เอง
→ ลบ 5 แถว · pf01 เหลือ 55 ช่องตรงกับที่ portal ส่ง

## บทเรียน — รูปแบบเดิมอีกครั้ง

วันเดียวกันเจอ 3 เคสที่เป็นรูปแบบเดียวกันเป๊ะ:

| เคส | ทำครบเฉพาะ | แบรนด์ที่ตกหล่น |
|---|---|---|
| `status` ไม่มีผลกับตัวซิงค์ ([[2026-08-19-retire-wwv02]]) | VMS | WW + Payif |
| ไม่แจ้งเตือนเปลี่ยนสินค้า ([[2026-08-19-slot-swap-alerts-missing]]) | VMS | WW + Payif |
| ไม่ลบช่องที่หายไป (เคสนี้) | **ไม่มีใครทำเลย** | ทั้ง 3 |

สองเคสแรกเกิดเพราะโค้ด VMS เขียนก่อน แล้วตอนเพิ่มแบรนด์ใหม่ต่อเฉพาะเส้นทางหลัก
เคสนี้หนักกว่า — **ไม่มีใครเคยคิดถึงเลยตั้งแต่แบรนด์แรก**

→ ครั้งหน้าเพิ่มแบรนด์ ให้ไล่เช็กลิสต์: sync ผ่าน · status มีผล · แจ้งเตือนทำงาน ·
**ช่องที่หายไปถูกลบ** · ยอดขาย map ครบ
