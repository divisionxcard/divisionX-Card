# ซิงค์สต็อกไม่อัปเดตมา 3 วัน โดยไม่มีสัญญาณเตือนเลย

เจ้าของเอา **รายงานเตรียมของเติมตู้** ของระบบมาเทียบกับ **ใบ Excel ที่แอดมินนับเองหน้าตู้**
แล้วพบว่าไม่ตรง — ทั้งตัวเลขคงเหลือและรายการสินค้าที่หายไปหลายตัว

## ต้นเหตุ: บั๊กที่ผมทำเองใน [[2026-08-21-sales-box-pack-split]]

ตอนแยกกล่อง/ซอง ผมเขียนตัวช่วย `upsert_sales()` แล้ว**ฮาร์ดโค้ด `ignore_duplicates=True`**

ค่านั้นถูกสำหรับตาราง `sales` — ตั้งใจกันเขียนทับ `product_name`/`sku_id` ของประวัติเก่า
หลังแอดมินเปลี่ยนสินค้าในช่อง (แถวเก่าต้องคงชื่อ ณ ตอนที่ขาย)

**แต่ผิดสำหรับ `machine_stock`** ซึ่งของเดิมไม่มีพารามิเตอร์นี้:

```python
# ของเดิม (ถูก)
supabase.table("machine_stock").upsert(batch, on_conflict="machine_id,slot_number")

# หลังผมแก้ (ผิด) — upsert_sales บังคับ ignore_duplicates=True
upsert_sales(supabase, batch, table="machine_stock", on_conflict="machine_id,slot_number")
```

`machine_stock` มี unique `(machine_id, slot_number)` — **ทุกช่องมีแถวอยู่แล้ว**
upsert จึงถูกข้ามทุกแถว ข้อมูลค้างที่ 21 ส.ค. 10:01 น. ตั้งแต่นั้น

## ทำไมไม่มีใครรู้ 3 วัน — นี่คือส่วนที่น่ากลัวที่สุด

- ❌ ไม่มี error
- ❌ workflow ขึ้น **เขียว** ทุกรอบ
- ❌ log พิมพ์ว่า **`🎉 บันทึกสำเร็จ 240 slots`**

PostgREST ตอบ 2xx ปกติเมื่อข้ามแถวซ้ำ ไม่ถือว่าผิด สคริปต์จึงพิมพ์จำนวนที่ **ส่งไป**
ไม่ใช่จำนวนที่ **เขียนจริง**

หลักฐานที่ชี้ขาด — นับ `synced_at` ในตาราง:

| วันที่ | แถว |
|---|---|
| 2026-08-17 | 55 |
| 2026-08-21 | 679 |
| 2026-08-22 | **1** |

แถวเดียวของ 22 ส.ค. คือ `wwv07/059` ซึ่งเป็น**ช่องใหม่** = INSERT เลยผ่านไปได้
ที่เหลือเป็น UPDATE ทั้งหมด → ถูกข้าม

**ยอดขายไม่กระทบ** เพราะ `sales` ตั้งใจใช้ `ignore_duplicates` อยู่แล้ว
(ยอดขายล่าสุดตอนตรวจคือ 23 ส.ค. 17:04 — เข้าปกติ) จึงไม่มีอะไรสะดุดตา

## วิธีไล่จนเจอ

1. เทียบรายงานกับ Excel → ต่างกันมากเกินกว่าจะเป็นการปัดเศษ
2. query `machine_stock` → `synced_at` ค้างที่ 21 ส.ค. ทุกตู้พร้อมกัน
3. ตรวจ GitHub Actions → **ทุก run เขียว** ← ตรงนี้เกือบหลงทาง
4. ดึง log จริงของ job → เห็นว่า login สำเร็จ ดึงข้อมูลได้ พิมพ์ว่าบันทึกสำเร็จ
5. เทียบ `git show bab932c~1` กับของปัจจุบัน → เจอ `ignore_duplicates` ที่เพิ่มเข้ามา

> ⚠️ **workflow เขียวไม่ได้แปลว่าข้อมูลเข้า** — ต้องเช็ก `synced_at`/`updated_at` ในตารางเสมอ

## แก้

เปิด `ignore_duplicates` เป็นพารามิเตอร์ · ค่าตั้งต้น `True` (สำหรับ `sales`)
ฝั่ง `machine_stock` ทั้ง 3 ไฟล์ส่ง `False` ให้ตรงกับพฤติกรรมเดิม
พร้อมเขียนกำกับในฟังก์ชันว่าตารางไหนใช้ค่าอะไรและเพราะอะไร

เจ้าของกดปุ่มซิงค์ใหม่ → **60/60 ช่องอัปเดต** และคงเหลือตรงกับใบแอดมิน **22/24 รายการ**
