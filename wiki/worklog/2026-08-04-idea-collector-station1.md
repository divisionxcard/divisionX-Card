# สถานี 1 — ระบบหาไอเดียคอนเทนต์

## บริบท (why)
หน้า /marketing เฟส 1+2 เริ่มต้นที่ "ร่างคอนเทนต์รออนุมัติ" เลย — **ขั้นหาไอเดียหายไปทั้งขั้น**
คนยังต้องนั่งคิดเองว่าจะทำคอนเทนต์เรื่องอะไร ซึ่งเป็นงานที่กินเวลาที่สุด

สถานีนี้เปลี่ยนจาก "นั่งคิดเอง" เป็น "AI ไปหามาวางบนโต๊ะให้เลือกทุกเช้า"

## เลือกแหล่งข้อมูลจากการทดสอบจริง ไม่ใช่จากที่คิดว่าน่าจะได้

ทดสอบก่อนออกแบบว่าแหล่งไหนดึงได้จริงโดย**ไม่ต้องมี API key** (เงื่อนไขสำคัญ —
ถ้าต้อง key จะรันบน GitHub Actions ไม่ได้ และต้องรอ approval):

| แหล่ง | ผล |
|---|---|
| Google News RSS ไทย | ✅ 55KB · ได้ข่าวตรงประเด็นมาก |
| YouTube channel RSS | ✅ 31KB · ใช้ `channel_id` ไม่ต้องมี key |
| Bandai One Piece TCG RSS | ❌ 404 — ตัดทิ้ง |
| คอมเมนต์ FB/YT | ⛔ ต้องขอ permission Meta → เฟส 3 |

**แหล่งที่ 3 คือข้อมูลขายของเราเอง** — แหล่งที่คู่แข่งลอกไม่ได้ เพราะไม่มีใครมีข้อมูลนี้

## ผล dry-run จริง (34 ไอเดียใหม่)

```
5.56 [internal] Pokemon Ninja กำลังมาแรง — ยอดโต 78%
5.50 [news    ] 10 อันดับ การ์ดวันพีช ที่ราคาแพงที่สุดในตลาด TCG
5.25 [internal] One Piece OP-13 กำลังมาแรง — ยอดโต 63%
4.70 [news    ] เปิดแล้ว! One Piece Card Game Pop-Up Store Bangkok แห่งแรกในไทย
3.90 [internal] One Piece OP-11 ยอดตก 45% — ควรกระตุ้น
```

ข่าว Pop-Up Store กรุงเทพฯ คือตัวอย่างที่ชัดว่าระบบมีประโยชน์จริง — เป็นกระแสที่เกี่ยวกับ
ธุรกิจโดยตรงและถ้าไม่มีตัวเก็บก็คงไม่รู้

## จุดตัดสินใจ

- **ให้คะแนนแบบ rule-based ไม่ใช้ LLM** — นับคำที่ตรงกับแฟรนไชส์ที่เราขายจริง
  (ดึงจากตาราง `skus` ไม่ hardcode) + คำบอกเจตนา (เปิดตัว/วางจำหน่าย/pop-up)
  เหตุผล: รันฟรี · ได้ผลเหมือนเดิมทุกครั้ง · และ Ollama รันบน Actions ไม่ได้อยู่แล้ว
- **แยกฟิลด์ `angle` กับ `relevance`** — `angle` คือมุมที่จะเล่า `relevance` คือทำไมเกี่ยวกับเรา
  สองอันนี้ทำให้สแกนแล้วตัดสินใจได้โดยไม่ต้องเปิดอ่านข่าวเต็ม (หลักการเดียวกับ `source_reason`
  ในกล่องอนุมัติ)
- **แหล่งข้อมูลอยู่ในไฟล์ JSON** (`deploy/tasks/idea_sources.json`) ไม่ใช่ในโค้ด —
  เพิ่มคำค้น/ช่อง YouTube ได้เองโดยไม่ต้องแก้ Python
- **"เริ่มทำคอนเทนต์" สร้างร่างสถานะ `draft` ไม่ใช่ `pending`** — เพราะตัวเขียนแคปชั่นจริง
  ใช้ Ollama ที่รันในเครื่องเท่านั้น เว็บทำได้แค่ตั้งโจทย์ให้ · กล่องอนุมัติจึงโหลด `draft,pending`
  แล้วติดป้าย **"ยังไม่มีแคปชั่นจริง"** กันเผลออนุมัติโจทย์แทนแคปชั่น
- **`external_key` unique** กันเก็บข่าวเดิมซ้ำข้ามรอบ · สัญญาณภายในผูกกับวันที่
  (`hot:OP 13:2026-08-04`) จึงเสนอได้วันละครั้ง ไม่รก

## เพิ่ม TikTok (b06aefa) — และเหตุผลที่ทำอัตโนมัติเต็มรูปแบบไม่ได้

ทดสอบทางเข้าถึงก่อนออกแบบ เหมือนรอบแรก:

| ทาง | ผล |
|---|---|
| Creative Center API (`creative_radar_api/.../hashtag/list`) | ❌ `{"code":40101,"msg":"no permission"}` |
| RSSHub public instance | ❌ 403 |
| oEmbed (`tiktok.com/oembed`) | ✅ ได้ title + author + thumbnail — แต่ต้องรู้ URL อยู่แล้ว |
| official Display/Research API | ⛔ ต้องสมัคร + รออนุมัติ |
| scrape เว็บ TikTok | ⛔ ผิด ToS + พังง่าย + ต้องใช้ headless browser — **ไม่ทำ** |

**สรุป: TikTok ไม่มีทางไล่หาคลิปไวรัลอัตโนมัติแบบฟรี ๆ** จึงทำ 2 ทางที่ได้จริง:

1. **`tiktok` source** — ดัก *ข่าวที่พูดถึงกระแส TikTok* ผ่าน Google News
   ได้ผลจริง 6 เรื่อง (การ์ดโปเกมอนยายมูลค่าล้าน · Gen Z ลงทุนการ์ด · คลิปเปิดการ์ดไวรัล)
   บวกคะแนน +0.5 เพราะกระแสไวรัลมีอายุสั้นกว่าข่าวทั่วไป
2. **ช่องวางลิงก์บนหน้าเว็บ** — เห็นคลิปเองตอนเลื่อนดูแล้ววาง URL
   ระบบดึงชื่อ/ผู้โพสต์/ปกให้ผ่าน **oEmbed** ซึ่งเป็นช่องทางสาธารณะที่แพลตฟอร์มเปิดให้เอง
   (ไม่ใช่ scrape) · รองรับทั้ง TikTok และ YouTube · ให้คะแนน 6 เพราะคนคัดมาแล้ว

> ทางที่ 2 สำคัญกว่าที่คิด — คลิปไวรัลที่ "เห็นกับตา" มักตรงกลุ่มเป้าหมายกว่าที่ระบบเดาให้
> และใช้เวลาแค่ copy-paste ไม่ต้องพิมพ์อะไรเลย

## ผลรันจริง
เก็บได้ **40 ไอเดีย** — ข่าว 26 · TikTok 6 · ภายใน 8 · รันซ้ำได้ 0 ใหม่ (idempotent ผ่าน)

จำลอง flow `pick` ที่ระดับ DB เพื่อพิสูจน์ schema (แล้วคืนสภาพเดิม):
`ไอเดีย → สร้าง marketing_content(draft) + โยง idea_id → ไอเดียเป็น picked` ✅
กล่องอนุมัติ query `status=in.(draft,pending)` เห็นร่างใหม่ทันที ✅

## แก้หลังเห็นหน้าจอจริง (c711587)

เปิดใช้แล้วเจอ 2 เรื่องที่ตอนเขียนโค้ดมองไม่ออก:

**1. ไอเดีย 40 ชิ้นรวดเดียวสแกนไม่ไหว**
ขัดกับธีสิสของหน้าเองที่ว่า "เปิดวันละ 2 ครั้ง ครั้งละไม่เกิน 5 นาที"
→ คัดเหลือ **3 ต่อช่องทาง** (เหลือ 9 จาก 39) เรียงตามคะแนนรวมอีกที
   chip บอก "แสดง/ทั้งหมด" + ปุ่มขยายเป็น 10 ถ้าอยากเห็นมากกว่านั้น

**2. แคปชั่นร่างยัด URL ข่าวยาว ~200 ตัวอักษรลงไป**
Google News redirect URL ยาวจนกลบเนื้อหา และข้อความในร่างซ้ำกับบรรทัด `💡 จาก:` ที่อยู่ล่างอยู่แล้ว
→ แคปชั่นร่างเหลือแค่ **"มุมที่จะเล่า"** อย่างเดียว · ลิงก์ย้ายไปเป็นปุ่ม **"ดูต้นทาง"**
   ดึงผ่าน embed `idea_id` — ต้องระบุชื่อ FK (`marketing_content_idea_id_fkey`)
   เพราะสองตารางอ้างกันไปกลับ PostgREST เลยเลือกไม่ถูก (PGRST201)

> บทเรียน: ทั้งสองข้อดูจากโค้ดไม่ออก ต้องเปิดหน้าจริงถึงเห็น

## คัดแบบวนประเภท (81676fb)

หลังคัดเหลือ 3 ต่อช่องทาง เจอปัญหาต่อ: **internal ได้ "SKU มาแรง" ทั้ง 3 อัน**
เพราะคะแนนสูงสุดหมด → "SKU ยอดตก" ที่ควรได้คอนเทนต์ดันไม่มีวันโผล่ขึ้นมาเลย
(เจ้าของธุรกิจชี้จุดนี้เอง — เป็นเรื่องธุรกิจ ไม่ใช่เรื่องเทคนิค)

แก้ด้วย **subtype + วนเลือกทีละประเภท** แทนหยิบคะแนนสูงสุดล้วน:

| ช่องทาง | subtype |
|---|---|
| internal | `hot_sku` · `falling_sku` · `restock` · `machine_drop` |
| news / tiktok | คำค้นที่ใช้ |
| youtube | ชื่อช่อง |

ผลจำลอง: **OP-11 ยอดตก 45% โผล่ขึ้นมาแล้ว** · ข่าว 3 ชิ้นมาจาก 3 คำค้นต่างกัน
· TikTok มาจาก 2 คำค้น ไม่กระจุกคำเดียว

> เลือกทำเป็น**คอลัมน์จริง** ไม่ใช่เดาจาก prefix ของ `external_key` — การคัดควรอิงค่าที่
> ตั้งใจเก็บ ไม่ใช่ผลข้างเคียงของรูปแบบ key ที่อาจเปลี่ยนทีหลัง

**ข้อจำกัดที่เห็นจากข้อมูลจริง:** ตอนนี้สัญญาณภายในมีแค่ มาแรง 7 · ยอดตก 1
(restock/ตู้ยอดตก = 0 เพราะไม่มีอะไรเข้าเกณฑ์) → วนได้แค่ 2 ประเภท คือ มาแรง 2 + ยอดตก 1
ยิ่งมีสัญญาณหลากหลาย การวนยิ่งได้ผล
