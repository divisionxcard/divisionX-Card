ตัวแปรที่น่าจะเป็นคำตอบ: **push ล่าสุดคือ 28 ก.ย. 19:56** คือ *ก่อน* ปลดแฟล็ก
→ ไม่มี activity ใด ๆ บน repo หลังปลด · การ push น่าจะเป็นตัวลงทะเบียนตาราง cron ใหม่

## 🔴 และห้าม push ทันที — เพราะจะได้โพสต์ซ้ำขึ้นเพจจริง

ช่วงที่ GitHub ตาย เราย้ายงานมาบอทในเครื่องหลายตัว **พอ Actions ฟื้น สองฝั่งจะทำงานเดียวกันพร้อมกัน**
ตัวที่อันตรายจริงคือโพสต์เพจ เพราะมันย้อนไม่ได้:

| | บอทในเครื่อง | `marketing-autopost.yml` |
|---|---|---|
| ความถี่ | ทุก 15 นาที | ทุก 15 นาที |
| ยิงไปที่ | `publish-due` | **URL เดียวกันเป๊ะ** |
| ติดอาวุธอยู่ไหม | ใช่ | ใช่ — `AUTOPOST_SECRET` ตั้งไว้ตั้งแต่ 17 ส.ค. |

**กลไกที่ทำให้ซ้ำได้จริง** (ไล่โค้ดจนเห็น ไม่ใช่กังวลลอย ๆ):

1. ด่านกันซ้ำคือ `.is("post_id", null)` — ประเมิน **ตอน SELECT**
2. `publishOne()` **ยิง Facebook ก่อน** (`publishToPage`) แล้ว*ค่อย*เขียน `status/posted_at/post_id`
3. ไม่มีการจองแถว (ไม่มี claim/lock) → ช่องว่างกว้างเท่าเวลาอัปรูปทั้งก้อน

คอมเมนต์ใน `publishContent.js` เตือนเรื่องนี้ไว้เองด้วย: *"ไม่งั้นจะมีคน (หรือ cron รอบถัดไป) ยิงซ้ำแล้วได้โพสต์ซ้ำบนเพจจริง"*

**ยังไม่เคยเกิด** เพราะ Actions ไม่ได้รันเลยตั้งแต่ 9 ก.ย. และตอนตรวจคิวว่าง (`approved/scheduled` = 0 ชิ้น)

> **งานเดียวกันสองตัวจับเวลา = ระเบิดเวลา** ไม่ใช่ "สำรองให้กันดี"
> ของที่ย้อนไม่ได้ (โพสต์ขึ้นเพจ · ส่งเมล · ตัดเงิน) ต้องมีเจ้าของเดียวเท่านั้น

### ⚠️ กับดัก `_*.py` ที่เกือบพลาด

จะเขียน `_*.py` เฉย ๆ แต่เช็กก่อนแล้วเจอว่า **`deploy/agents/_console.py` เป็นไฟล์ที่ track อยู่จริง**
และ `__init__.py` ก็ขึ้นต้นด้วย `_` เหมือนกัน → ถ้าเขียนลอย ๆ ไฟล์ซอร์สใหม่จะหายเงียบในอนาคต

```gitignore
_*.py
!__init__.py
!__main__.py
!deploy/agents/_console.py
```

ทดสอบด้วย `git check-ignore` ทั้งสองทาง — ไฟล์ที่ต้อง track ต้องไม่ติด · ไฟล์ขยะต้องติด

> **ก่อนเพิ่มรูปแบบใหม่ใน .gitignore ให้ `git ls-files` ดูก่อนว่ามันกลืนของจริงไหม**
> gitignore ไม่มีผลกับไฟล์ที่ track แล้ว จึงทดสอบแล้ว "ดูปกติ" ทั้งที่กฎผิด — ของที่พังคือไฟล์ใหม่วันหน้า
