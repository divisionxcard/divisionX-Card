# บั๊ก 2 ตัวที่หลุดถึงมือผู้ใช้ — และช่องโหว่ในวิธีทดสอบของผม

ทั้งสองตัวเจ้าของเป็นคนเจอเองจากการกดใช้งาน ไม่ใช่เทสต์จับได้
ประเด็นสำคัญไม่ใช่ตัวบั๊ก แต่คือ **ทำไมเทสต์ถึงผ่านทั้งที่ของพัง**

## บั๊ก 1 — `p.from(...).in is not a function`

กดปุ่ม "ให้ AI เขียน" แล้วพังทันที **ทุกครั้ง ตั้งแต่ commit `95666cd`**

```js
db.from(t).in(...).select(...)   // ❌ from() คืน query builder ที่ยังไม่มี .in()
db.from(t).select(...).in(...)   // ✅ ตัวกรองอยู่บน filter builder หลัง select
```

### ทำไมเทสต์ไม่จับ
วิธีทดสอบที่ใช้อยู่คือดึงฟังก์ชันล้วนออกมา `eval` แล้วยิง provider ตรง
ซึ่งตั้งใจเลี่ยง `import` เพื่อไม่ให้ไปต่อ network —
**แต่นั่นแปลว่ามันเลี่ยงการทดสอบทุกอย่างที่ต่อ network ไปด้วย**
`fetchRecent()` ไม่เคยถูกรันเลยสักครั้ง

รอบแก้ทดสอบด้วย `@supabase/supabase-js` ตัวจริงต่อ DB จริง — reproduce error
เดิมได้ตรงกับที่เจ้าของเจอ แล้วยืนยันว่าโครงใหม่คืน 6 แถวไม่ error

## บั๊ก 2 — กดอนุมัติแล้วขึ้น `unauthorized`

เปิดหน้าค้างไว้นาน ๆ แล้วกดปุ่มใด ๆ จะขึ้น `unauthorized`
**ทั้งที่ยัง login อยู่และเป็น admin**

`MarketingOS` ดึง `access_token` ตอน mount ครั้งเดียวแล้วเก็บใส่ React state
ใช้ตัวนั้นยิงทุก request — แต่ token ของ Supabase หมดอายุใน ~1 ชม.
client ต่ออายุให้เองเบื้องหลังก็จริง **แต่ค่าที่ copy ไปเก็บใน state ไม่ได้ต่อตาม**

### วิธีแยกแยะที่ช่วยได้เร็ว
```
"unauthorized" (401) = token ไม่ถูก/หมดอายุ  → requireUser
"forbidden"    (403) = login แล้วแต่ role ไม่ใช่ admin → requireAdmin
```
คนละข้อความคนละสาเหตุ — เห็นคำไหนก็รู้ทันทีว่าไปดูตรงไหน
ยืนยันด้วยการยิง route ด้วย token มั่ว → ได้ 401 `unauthorized` ตรงกับที่เจ้าของเจอ

**แก้:** `api()` เรียก `supabase.auth.getSession()` ทุกครั้งเพื่อเอาตัวล่าสุด
(getSession ต่ออายุให้เองถ้าใกล้หมด) + ดัก 401 พากลับหน้า login
พร้อมข้อความ **"เซสชันหมดอายุ"** แทนคำว่า unauthorized ที่คนอ่านไม่รู้เรื่อง

จงใจไม่ `setToken()` ใน `api()` เพราะจะทำให้ callback ถูกสร้างใหม่ →
`loadAll` ใหม่ → โหลดซ้ำโดยไม่จำเป็น · state `token` เหลือหน้าที่เป็นแค่ธง "ล็อกอินแล้ว"

ตรวจทั้งโปรเจกต์แล้ว **มีที่เดียว**ที่ส่ง token ของผู้ใช้จากฝั่ง client
ที่เหลือเป็น `GH_PAT` / service key / token ของ vendor ซึ่งเป็นฝั่ง server คนละเรื่อง

## บทเรียน

**เทสต์ที่เลี่ยง network เพื่อความเร็ว = เทสต์ที่ไม่ได้ทดสอบชั้น I/O เลย**
รู้ตัวว่าใช้วิธีนี้แล้วต้องแยกทดสอบชั้นที่มันข้ามไปต่างหาก ไม่ใช่ถือว่าครอบคลุมแล้ว

และ **"ทดสอบผ่าน" ต้องบอกให้ชัดว่าผ่านอะไร** — รอบก่อนผมรายงานว่า
"ทดสอบผ่านสคริปต์ที่เรียก Gemini ตรง" ซึ่งเป็นความจริง แต่ไม่ได้สื่อว่า
เส้นทางนั้นข้าม DB ทั้งหมด ทำให้ดูน่าเชื่อถือเกินจริง

บันทึกกฎลง `.claude/skills/dvx-content` แล้ว: แตะโค้ดที่ query DB ต้องรันกับ client จริง
