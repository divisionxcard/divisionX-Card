# ฐานข้อมูลเปิดให้ใครก็ลบยอดขายได้ — มาตั้งแต่วันแรกของโปรเจกต์

Supabase ส่งอีเมลเตือน 23 ส.ค. ว่า `rls_disabled_in_public` + `sensitive_columns_exposed`
เจ้าของส่งมาให้ตรวจว่าร้ายแรงแค่ไหน

**ร้ายแรงกว่าที่อีเมลบอก**

## วิธีตรวจที่ให้คำตอบจริง

ทดสอบด้วย **anon key ไม่ใช่ service key** — service key ข้าม RLS อยู่แล้ว
ทดสอบด้วยตัวนั้นจะไม่เห็นช่องโหว่เลยแม้แต่นิดเดียว

anon key อยู่ใน bundle ของหน้าเว็บ (`NEXT_PUBLIC_SUPABASE_ANON_KEY`)
ใครเปิด DevTools ก็เห็น — **ไม่ใช่ความลับโดยการออกแบบ** Supabase ตั้งใจให้เปิดเผย
ความปลอดภัยต้องมาจาก RLS เท่านั้น ซึ่งไม่เคยถูกเปิดเลย

## ตรวจก่อนแก้ว่าเปิด RLS แล้วเว็บจะพังไหม

การเปิด RLS โดยไม่มี policy = เว็บพังทั้งระบบ ต้องรู้ก่อนว่าอะไรพึ่ง anon อยู่บ้าง

| | ผล |
|---|---|
| หน้าสาธารณะ `/branches` `/products` `/how-to` `/marketing` `/design-system` | static ทั้งหมด **ไม่ query Supabase จากเบราว์เซอร์เลย** |
| username → email ตอนล็อกอิน | ผ่าน `/api/auth/lookup-email` ฝั่งเซิร์ฟเวอร์ (service key) |
| API route ทุกตัว | service key → ข้าม RLS |
| scraper / GitHub Actions | service key → ข้าม RLS |

**ไม่มีอะไรพึ่งสิทธิ์ anon เลยแม้แต่จุดเดียว** จึงเปิดได้ทันทีโดยไม่ต้องแก้โค้ดสักบรรทัด

## migration 069

ตั้งให้เท่ากับพฤติกรรมเดิม "ยกเว้นต้องล็อกอินก่อน" — `authenticated` ทำได้ทุกอย่าง ·
`anon` ทำอะไรไม่ได้ + `REVOKE ALL FROM anon` เป็นเกราะชั้นสอง เผื่อวันหน้าใครเผลอปิด RLS

**View ต้องจัดการแยก** — RLS ไม่มีผลกับ view เพราะ view รันด้วยสิทธิ์เจ้าของ
(security definer) จึงข้าม RLS ของตารางข้างใต้ไปเลย ถ้าเปิด RLS อย่างเดียว
`v_daily_sales` จะยังรั่ว 11,174 แถว → ต้องสั่ง `security_invoker = on`

## ⚠️ ตัวตรวจของผมเองพลาด 2 รอบ — บันทึกไว้เพราะอันตราย

**รอบ 1 — false negative (อันตรายที่สุด)**
เช็กว่าอ่านได้ไหมด้วย `rc == 200` แต่ PostgREST คืน **206 Partial Content** เมื่อมีแถว
มากกว่าที่ `Range` ขอ → ตารางที่มีข้อมูลถูกรายงานว่า "🟢 บล็อก" ทั้งที่อ่านได้หมด
รายงานว่ารั่วแค่ 6 ตาราง ทั้งที่จริง 22

ถ้าไม่จับได้ จะสรุปให้เจ้าของว่าช่องโหว่เล็กกว่าจริง 4 เท่า

**รอบ 2 — false positive** (หลังรัน migration แล้ว)
รายงานว่ายังลบได้ 4 ตัว ตรวจลึกแล้วไม่จริงสักตัว:
- `profiles` / `slot_restock_sessions` — `id` เป็น **uuid** แต่ยิง `id=eq.-999999`
  → ตาย `22P02` ตั้งแต่ก่อนถึงชั้นสิทธิ์ · ยิงซ้ำด้วยรูปแบบ uuid ได้ `42501` = บล็อกจริง
- `v_daily_sales` / `v_stock_balance` — ไม่มีคอลัมน์ `id` (`42703`) และต่อให้ยิงถูก
  ก็ได้ `55000 Views containing GROUP BY are not automatically updatable`
  ซึ่งเป็นข้อจำกัดเชิงโครงสร้าง ไม่ใช่ช่องโหว่

แก้โดยแยกผลการเขียนเป็น **3 สถานะ** แทน 2: `blocked` / `n/a` / `open`

> 💡 **เทสต์ความปลอดภัยที่เตือนหลอกจะไม่มีใครเชื่อ รอบหน้าคนจะข้ามมันไป**
> ต้องแยกให้ออกระหว่าง "ปลอดภัย" กับ "ทดสอบไม่ได้" — สองอย่างนี้ไม่เหมือนกัน
> และต้องอ่าน **SQLSTATE** ไม่ใช่แค่รหัส HTTP
