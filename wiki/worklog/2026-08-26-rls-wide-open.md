# ฐานข้อมูลเปิดให้ใครก็ลบยอดขายได้ — มาตั้งแต่วันแรกของโปรเจกต์

Supabase ส่งอีเมลเตือน 23 ส.ค. ว่า `rls_disabled_in_public` + `sensitive_columns_exposed`
เจ้าของส่งมาให้ตรวจว่าร้ายแรงแค่ไหน

**ร้ายแรงกว่าที่อีเมลบอก**

## วิธีตรวจที่ให้คำตอบจริง

ทดสอบด้วย **anon key ไม่ใช่ service key** — service key ข้าม RLS อยู่แล้ว
ทดสอบด้วยตัวนั้นจะไม่เห็นช่องโหว่เลยแม้แต่นิดเดียว

anon key อยู่ใน bundle ของหน้าเว็บ (`NEXT_PUBLIC_SUPABASE_ANON_KEY`)
ใครเปิด DevTools ก็เห็น — **ไม่ใช่ความลับโดยการออกแบบ** Supabase ตั้งใจให้เปิดเผย
ความปลอดภัยต้องมาจาก RLS เท่านั้น ซึ่งไม่เคยถูกเปิดเลย

## ตรวจก่อนแก้ว่าเปิด RLS แล้วเว็บจะพังไหม

การเปิด RLS โดยไม่มี policy = เว็บพังทั้งระบบ ต้องรู้ก่อนว่าอะไรพึ่ง anon อยู่บ้าง

| | ผล |
|---|---|
| หน้าสาธารณะ `/branches` `/products` `/how-to` `/marketing` `/design-system` | static ทั้งหมด **ไม่ query Supabase จากเบราว์เซอร์เลย** |
| username → email ตอนล็อกอิน | ผ่าน `/api/auth/lookup-email` ฝั่งเซิร์ฟเวอร์ (service key) |
| API route ทุกตัว | service key → ข้าม RLS |
| scraper / GitHub Actions | service key → ข้าม RLS |

**ไม่มีอะไรพึ่งสิทธิ์ anon เลยแม้แต่จุดเดียว** จึงเปิดได้ทันทีโดยไม่ต้องแก้โค้ดสักบรรทัด

## migration 069

ตั้งให้เท่ากับพฤติกรรมเดิม "ยกเว้นต้องล็อกอินก่อน" — `authenticated` ทำได้ทุกอย่าง ·
`anon` ทำอะไรไม่ได้ + `REVOKE ALL FROM anon` เป็นเกราะชั้นสอง เผื่อวันหน้าใครเผลอปิด RLS

**View ต้องจัดการแยก** — RLS ไม่มีผลกับ view เพราะ view รันด้วยสิทธิ์เจ้าของ
(security definer) จึงข้าม RLS ของตารางข้างใต้ไปเลย ถ้าเปิด RLS อย่างเดียว

## ⚠️ ตัวตรวจของผมเองพลาด 2 รอบ — บันทึกไว้เพราะอันตราย

**รอบ 1 — false negative (อันตรายที่สุด)**
เช็กว่าอ่านได้ไหมด้วย `rc == 200` แต่ PostgREST คืน **206 Partial Content** เมื่อมีแถว
มากกว่าที่ `Range` ขอ → ตารางที่มีข้อมูลถูกรายงานว่า "🟢 บล็อก" ทั้งที่อ่านได้หมด
รายงานว่ารั่วแค่ 6 ตาราง ทั้งที่จริง 22

ถ้าไม่จับได้ จะสรุปให้เจ้าของว่าช่องโหว่เล็กกว่าจริง 4 เท่า

**รอบ 2 — false positive** (หลังรัน migration แล้ว)
รายงานว่ายังลบได้ 4 ตัว ตรวจลึกแล้วไม่จริงสักตัว:
- `profiles` / `slot_restock_sessions` — `id` เป็น **uuid** แต่ยิง `id=eq.-999999`
  → ตาย `22P02` ตั้งแต่ก่อนถึงชั้นสิทธิ์ · ยิงซ้ำด้วยรูปแบบ uuid ได้ `42501` = บล็อกจริง
- `v_daily_sales` / `v_stock_balance` — ไม่มีคอลัมน์ `id` (`42703`) และต่อให้ยิงถูก
  ก็ได้ `55000 Views containing GROUP BY are not automatically updatable`
  ซึ่งเป็นข้อจำกัดเชิงโครงสร้าง ไม่ใช่ช่องโหว่

แก้โดยแยกผลการเขียนเป็น **3 สถานะ** แทน 2: `blocked` / `n/a` / `open`

> 💡 **เทสต์ความปลอดภัยที่เตือนหลอกจะไม่มีใครเชื่อ รอบหน้าคนจะข้ามมันไป**
> ต้องแยกให้ออกระหว่าง "ปลอดภัย" กับ "ทดสอบไม่ได้" — สองอย่างนี้ไม่เหมือนกัน
> และต้องอ่าน **SQLSTATE** ไม่ใช่แค่รหัส HTTP

# ภาคต่อ — เปิด RLS แล้วหน้าสาธารณะ 2 หน้าว่างเปล่า (ผมตรวจไม่ครบเอง)

เจ้าของแจ้งว่า `/branches` กับ `/products` เปิดจากลิงก์ไม่ได้แล้ว
**สองหน้านี้คือหน้าที่ลูกค้ากดมาจากโซเชียลเพื่อดูสาขาและสินค้า** — พังคือกระทบยอดขายตรง ๆ

## ผมตรวจพลาดตรงไหน

ก่อนทำ migration 069 ผมสรุปว่า *"หน้าสาธารณะเป็น static ทั้งหมด ไม่ query Supabase"*
โดย grep หา `from "@/lib/supabase"` กับ `createClient` ใน `page.jsx` แล้วได้ 0

**แต่สองหน้านี้ยิง `fetch()` ตรง ๆ พร้อม anon key** ไม่ได้ import อะไรเลย

```js
const key = process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY
const res = await fetch(`${url}/rest/v1/machines?...`, { headers: { apikey: key, ... } })
if (!res.ok) return []
```

> 💡 **grep หา "วิธีเรียกใช้" ไม่พอ ต้อง grep หา "สิ่งที่ถูกใช้"**
> ถ้าค้น `NEXT_PUBLIC_SUPABASE_ANON_KEY` ตั้งแต่แรกก็เจอทันที
> รอบหน้าที่จะปิดสิทธิ์อะไร ให้ไล่จาก **ตัวความลับ** ไม่ใช่จากชื่อ module

## แล้วทำไม curl ตอบ 200 ทั้งที่พัง

ทั้งสองหน้าเขียน `if (!res.ok) return []` กับ `catch { return [] }` — ออกแบบมาให้
หน้าไม่ล่มเวลาดึงข้อมูลไม่ได้ ซึ่งดีสำหรับผู้ใช้ **แต่ทำให้ผมตรวจผิด**
ผมยิง curl เห็น 200 แล้วรายงานเจ้าของว่า "หน้าสาธารณะยังเปิดได้ปกติ" ทั้งที่ว่างเปล่าไปแล้ว

**บทเรียน: หน้าที่ fallback แบบเงียบ ต้องตรวจ "เนื้อหา" ไม่ใช่ "รหัสตอบกลับ"**

## วิธีแก้ที่เลือก — และที่ไม่เลือก

ทั้งสองหน้าเป็น **server component** (ไม่มี `"use client"`) ดึงข้อมูลตอน build/ISR
ฝั่งเซิร์ฟเวอร์ → ใช้ `SUPABASE_SERVICE_ROLE_KEY` ได้ ปลอดภัยเพราะคีย์ไม่ไปเบราว์เซอร์

**ที่ไม่เลือก: เปิดสิทธิ์ anon ให้ตาราง `skus`**
RLS เป็น row-level ไม่ใช่ column-level — เปิดอ่านเมื่อไหร่ คนนอกเห็น **`cost_price`**
ซึ่งเป็นต้นทุนของเรา ทั้งที่หน้าเว็บใช้แค่ชื่อ/ราคาขาย/รูป

เพิ่ม `deploy/lib/publicPageData.js` รวมตรรกะไว้ที่เดียว และ **log ให้ดัง**
เมื่อดึงไม่ได้ (HTTP กี่ · error อะไร · หรือ "ได้ 0 แถว") ดูได้ที่ Vercel → Logs
รากของปัญหารอบนี้คือมันพังเงียบทั้งวันโดยไม่มีสัญญาณ

## พิสูจน์ว่า service key ไม่หลุด

คำถามของเจ้าของ: *"สองหน้านี้เสี่ยงให้คนเข้าถึงเว็บหลักไหม"*

ตรวจ HTML + ไฟล์ JS ทุกก้อนของ production รวม **2.3 ล้านตัวอักษร**:

| หน้า | service key | anon key |
|---|---|---|
| `/branches` | 🟢 ไม่พบ | ไม่พบ |
| `/products` | 🟢 ไม่พบ | ไม่พบ |
| `/` (แอปหลัก) | 🟢 ไม่พบ | พบ (ปกติ ออกแบบมาให้เปิดเผย) |

สองหน้าสาธารณะ **ไม่มีคีย์อะไรเลย** เป็น HTML ที่ render เสร็จจากเซิร์ฟเวอร์ล้วน ๆ

## ⚠️ ตัวตรวจการรั่วก็พลาดอีกรอบ

รอบแรกรายงานว่า service key หลุด**ทุกหน้า** รวมหน้า `/` ที่ไม่ได้แก้ — ผิดทั้งหมด

สาเหตุ: ผมตัดคีย์ช่วง `[40:90]` มาเป็นลายเซ็น โดยคิดว่าคีย์เป็น JWT ยาว ๆ
แต่ **Supabase เปลี่ยนมาใช้รูปแบบใหม่ที่ยาวแค่ 41/46 ตัวอักษร**
→ ลายเซ็นเหลือ **1 ตัวอักษร** ซึ่งเจอในไฟล์ไหนก็ได้

แก้โดยค้นด้วยคีย์เต็ม ผลกลับเป็นตรงข้าม

> 💡 นี่เป็นครั้งที่ 3 ของวันที่ตัวตรวจของผมเองให้ผลผิด (206 · uuid · ความยาวคีย์)
> จุดร่วม: **ผมสมมติรูปแบบของข้อมูลแทนที่จะวัดก่อน**
> เครื่องมือตรวจความปลอดภัยต้องพิสูจน์ตัวเองว่าจับของเสียได้จริงก่อนเชื่อผลมัน

# ภาคต่อ 2 — "ทั้ง 11 สาขา" ที่ค้างมาไม่รู้กี่เดือน

เจ้าของทักว่าหน้า `/products` เขียน *"ทั้ง 11 สาขา"* ไม่ตรงกับความจริง

ตรวจแล้ว: ตู้ `active` **12 ตู้** (wwv02 ปิดไปแล้ว) และทุกตู้ตั้ง `config.branch.public = true`
→ ของจริงคือ **12 สาขา**

| หน้า | นับยังไง | ผลก่อนแก้ |
|---|---|---|
| `/branches` | `BRANCHES.length` จาก DB | ✅ 12 (ถูกมาตลอด) |
| `/products` | **เลขตายตัวในโค้ด** | ❌ 11 |
| `/how-to` | **เลขตายตัวในโค้ด** | ❌ 11 |

> 💡 ตอนเขียนเลข 11 มันถูก — แต่พอเปิดตู้เพิ่มก็ไม่มีใครกลับมาแก้
> **เลขที่ต้องอัปเดตด้วยมือ = เลขที่จะผิดในที่สุด** ยิ่งเป็นหน้าที่แชร์ออกโซเชียล
> ยิ่งเสียความน่าเชื่อถือ เพราะสองหน้าบอกไม่ตรงกันเอง

แก้โดยเพิ่ม `branchCount()` ใน `lib/publicPageData.js` นับด้วยเงื่อนไขเดียวกับที่
`/branches` ใช้แสดงการ์ด แล้วให้ทั้งสองหน้าเรียกใช้
(`/how-to` ต้องเปลี่ยนเป็น async component + ใส่ `revalidate = 60`)

## กับดักที่โผล่ตามมา — ยิงพลาดครั้งเดียว หน้าหายข้อมูลทั้งนาที

หลัง deploy พบว่า `/products` **ไม่แสดงเลขเลย** ทั้งที่ `/how-to` แสดง 12 ปกติ

ไม่ใช่บั๊กตรรกะ — render รอบแรกหลัง deploy ยิง `machines` พลาดครั้งเดียว (cold start)
`fetchPublic` คืน `[]` ตามที่ออกแบบ แล้ว **ผลว่างนั้นถูก ISR cache ไว้ 60 วินาที**
พอ revalidate รอบถัดไปก็กลับมาเอง = พังชั่วคราวแบบไม่มีใครรู้

→ เพิ่ม retry 1 ครั้ง (หน่วง 400ms) · ถ้าได้ 0 แถวจริงไม่ลองซ้ำ (ข้อมูลว่างจริง
ไม่ใช่ความผิดพลาด) · ล้มทั้ง 2 ครั้งค่อย log ว่าหน้าจะไม่ครบ

ตรวจหลังแก้ 3 รอบห่างกัน 40 วินาที: `/products` `/how-to` `/branches` ตรงกันเป็น **12** ทุกรอบ
