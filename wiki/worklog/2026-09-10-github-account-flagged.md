# บัญชี GitHub ถูกแฟล็ก — และผมเป็นคนทำให้เกิด

## เกิดอะไรขึ้น

คืนวันที่ 9 ก.ย. ระหว่างสร้าง[[โรงงานวิดีโอ|2026-09-09-video-studio]] เสร็จแล้วจะยิงงาน
ทดสอบผ่าน GitHub Actions ก็เจอว่า:

```
POST .../actions/workflows/{id}/dispatches
→ 422 "Actions has been disabled for this user."
```

## ผมไล่ผิดทางอยู่ 3 รอบ

| รอบ | สรุปว่า | ผิดตรงไหน |
|---|---|---|
| 1 | "GitHub ปิด Actions ทั้งบัญชี ทุกอย่างหยุดหมด" | หน้าเว็บเห็น 2,649 runs เขียวหมด — **ไม่มีอะไรหยุด** |
| 2 | "เป็นเพราะ fine-grained token ต้องเปลี่ยนเป็น classic" | เปลี่ยนแล้วได้ 422 เหมือนเดิม |
| 3 | "GitHub มีปัญหาฝั่งเขา / ต้องรอ support" | มีหลักฐานชี้ตัวจริงอยู่แล้วแต่ไม่ได้ดู |

**ตัวเลขที่ควรดูตั้งแต่นาทีแรก** — และเป็นตัวที่ปิดจ๊อบในที่สุด:

```
x-ratelimit-limit: 60      ← ระดับ "คนไม่ได้ล็อกอิน"
                             บัญชีที่ยืนยันตัวตนแล้วต้องได้ 5,000
```

ทั้งที่ `GET /user` ตอบ 200 พร้อม `login: divisionxcard` — คือ **GitHub รู้ว่าเราเป็นใคร
แต่ไม่นับสถานะผู้ใช้ให้**

## หลักฐานชุดที่ทำให้เห็นภาพครบ

- โควตา **60/ชม.** แทน 5,000 ทั้งที่ auth ผ่าน
- หน้า token ขึ้น **"Never used"** ทั้งที่เพิ่งยิงสำเร็จหลายสิบครั้ง
- `GET /actions/permissions` ตอบ `{"enabled": true}` แต่ dispatch ตอบ 422 — **GitHub ขัดกันเอง**
- **`github.com/divisionxcard` และหน้า repo ตอบ 404 เมื่อดูแบบไม่ล็อกอิน**
  (ตอนบ่ายยังเปิดได้ปกติ) → นี่คือเหตุผลที่ **Vercel deploy ไม่ได้** ด้วย มันมองไม่เห็น repo แล้ว
- security log **ไม่มีเหตุการณ์อะไรเลย** — แฟล็กอัตโนมัติไม่ถูกบันทึกให้เจ้าของเห็น

ตัวที่ยืนยันชัดที่สุดคือหน้า support เอง:

> *"As your account **has been flagged**, we ask that you enable two-factor authentication (2FA)"*

## ต้นเหตุ

คืนนั้นผมยิง GitHub API ถี่มาก — ทั้งตอนไล่หาสาเหตุ และตอนกระจายงาน **12 agent ที่ใช้ 472
tool call** บนบัญชีที่เพิ่งเปิดเมื่อ เม.ย. 2026 ระบบตรวจจับอัตโนมัติจึงมองว่าผิดปกติ

**นี่ไม่ใช่อุบัติเหตุที่หลีกเลี่ยงไม่ได้** — เป็นผลจากการเลือกวิธีทำงานของผมเอง

## บทเรียน

**1. เวลาเจออาการแปลก ให้ดู "โควตา" ก่อนสรุปว่าอะไรพัง**
`x-ratelimit-limit` บอกความจริงตั้งแต่คำขอแรก ถ้าดูตั้งแต่ต้นจะประหยัดไป 3 ชั่วโมง

**2. API ที่มีโควตา = ห้ามกระจาย agent เข้าไปรุม**
ตอนไล่ปัญหานี้ผมตั้งใจ**ไม่**ใช้ workflow กระจายงาน เพราะเหลือโควตา 60 ครั้ง/ชม. —
การส่ง agent หลายตัวไปยิงพร้อมกันคือทำให้แย่ลง ไม่ใช่เร็วขึ้น
เครื่องมือที่แรงกว่าไม่ได้แปลว่าเหมาะกว่า

**3. "หน้าเว็บใช้ได้" กับ "API ใช้ได้" เป็นคนละเรื่อง**
session ของเบราว์เซอร์กับโทเคนเดินคนละเส้น เห็นหน้าเว็บปกติแล้วสรุปว่าไม่มีปัญหา
หรือเห็น API พังแล้วสรุปว่าระบบล่ม — ผิดทั้งคู่ ต้องเช็กทั้งสองฝั่งเสมอ

**4. ยอมรับตรง ๆ ในเคส support**
ในคำร้องเขียนไปตรง ๆ ว่าคืนนั้นมีการยิง API ถี่ผิดปกติจริง แต่เป็นงานพัฒนาบน repo ตัวเอง
และหยุดแล้ว — ปล่อยให้เขาไปสงสัยเองมีแต่ทำให้ช้า

## สิ่งที่ทำไปแล้ว

1. เปิด **2FA** (เป็นเงื่อนไขที่ GitHub บังคับก่อนให้ติดต่อ support) + เก็บ recovery codes ไว้นอก repo
   — repo นี้ public การเก็บกุญแจสำรองไว้ในโฟลเดอร์เดียวกับที่ `git add -A` เอื้อมถึงคือความเสี่ยงที่ไม่ควรรับ
2. เปิดเคส **Reinstatement request** (10 ก.ย. 01:20 น.) แนบ request ID `D10F:1BC022:2B767:2E190:6AA19BB4`
3. ทำ [[ตัวรันซิงค์สำรองในเครื่อง|scripts/sync_local.py]] เผื่อ cron หยุดจริง (ยังไม่ต้องใช้)
4. **หยุดยิง GitHub API** ตั้งแต่ 01:00 น.
