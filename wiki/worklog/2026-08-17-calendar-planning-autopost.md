# ปฏิทินโพสต์ที่ AI วางแผนได้ + โพสต์เองเมื่อถึงเวลา

เจ้าของขอสองอย่าง: ให้ Hermes วางแผนลงปฏิทินโพสต์ และให้ระบบโพสต์เองหลังตรวจงานเสร็จ

ของเดิมมีถึง "ปุ่มโพสต์ขึ้นเพจ" ([[auto-posting-level3-setup]]) แต่ยังต้องมีคนกดทุกครั้ง
**ไม่มีตัวจับเวลา** — สิ่งที่ขาดคือคนกดปุ่มตอนถึงเวลา ไม่ใช่ความสามารถในการโพสต์

## ตัดสินใจอะไรไว้ และเพราะอะไร

### ตัวจับเวลาอยู่บนคลาวด์ ไม่ใช่ในเครื่องเจ้าของ

Hermes รันบนเครื่องเจ้าของ ถ้าให้มันเป็นคนยิงโพสต์ตอนถึงเวลา **โพสต์จะไม่ขึ้นถ้าคอมปิด**
ซึ่งขัดกับจุดประสงค์ของการตั้งเวลาทั้งหมด

จึงแยกหน้าที่: **Hermes วางแผน (ในเครื่อง) · GitHub Actions ยิงตามเวลา (คลาวด์)**
workflow เป็นแค่ตัวจับเวลาที่ไปเคาะประตู ตัวตัดสินใจว่าโพสต์ชิ้นไหนอยู่ฝั่งเว็บทั้งหมด

### ด่านกันพลาดต้องมีชุดเดียว

ย้ายตรรกะ "โพสต์ 1 ชิ้น" ไป [`lib/publishContent.js`](../../deploy/lib/publishContent.js)
ให้ทั้งปุ่มคนกดและตัวตั้งเวลาเรียกตัวเดียวกัน

เหตุผลไม่ใช่ความสวยงามของโค้ด — **ถ้าเขียนสองที่ วันหนึ่งเพิ่มด่านใหม่ที่ทางเดียว
ทางที่ลืมจะปล่อยของเสียขึ้นเพจจริง** และโพสต์แล้วลบไม่ได้
(บทเรียนเดิม: [[project_sku_mapping_two_scraper_maps]] ตรรกะซ้ำสองชุดพังแบบเงียบ ๆ)

**ด่านที่ต่างกันจงใจข้อเดียว:** ตัวตั้งเวลาไม่โพสต์ชิ้นที่ผู้ตรวจให้ `drop`
ส่วนคนกดเองไม่บล็อก — เขาเห็นป้ายเตือนบนหน้าจอแล้วยังยืนยัน นั่นคือการตัดสินใจของเขา
แต่ตอน cron ยิงไม่มีใครดูอยู่ จึงต้องระวังกว่า

### เพดาน 2 ชิ้นต่อรอบ

รอบละ 15 นาที = เพดาน 8 โพสต์/ชม. ซึ่งมากกว่าที่เพจต้องใช้จริงหลายเท่า
มีไว้จำกัดความเสียหายกรณีวันหนึ่งตั้งเวลาผิดยกล็อต ไม่ใช่เพื่อ throughput

### ด่านตั้งเวลาอยู่ที่ชั้นข้อมูล ไม่ฝากไว้กับวินัยของ agent

`schedule_content` ปฏิเสธเองเมื่อ:

| เงื่อนไข | เพราะ |
|---|---|
| เวลาย้อนหลัง | ระบบจะโพสต์ทันทีในรอบถัดไป = ไม่ใช่การวางแผน |
| ห่างของเดิมน้อยกว่า 45 นาที | คนตามอ่านไม่ทัน และดูเหมือนสแปม |
| ผู้ตรวจให้ `drop` | ต้องยืนยันด้วย `force=True` ซึ่ง SOUL.md ห้าม agent ใช้เอง |
| สถานะ posted/rejected | ไม่มีความหมาย |

เขียนกฎไว้ใน prompt ด้วยก็ได้ แต่ prompt ไม่ใช่ด่าน — โมเดลลืมได้ โค้ดลืมไม่ได้

## สถานะ: ยังปิดอยู่โดยตั้งใจ

ไม่มี `AUTOPOST_SECRET` → ปลายทางตอบ **503** และ workflow ข้ามรอบเงียบ ๆ (ไม่ถือว่าล้มเหลว)
เปิดใช้ = ตั้งค่าเดียวกันสองที่: **env บน Vercel** + **GitHub secret**
(ค่าถูกสร้างไว้แล้วใน `deploy/.env.local`)

การเปิดสวิตช์จึงเป็นการตัดสินใจของเจ้าของ ไม่ใช่ผลข้างเคียงของการ deploy

## ทดสอบแล้ว

```
publish-due ไม่มี secret        → 503 พร้อมบอกวิธีเปิด
publish-due secret ผิด          → 401
publish-due secret ถูก          → 200 · posted 0 (ยังไม่มีอะไรถึงคิว)
publish (ปุ่มคนกด) ไม่ล็อกอิน    → 401 (ยัง gate admin เหมือนเดิม)
schedule_content เวลาย้อนหลัง    → ปฏิเสธ
schedule_content รูปแบบเวลาผิด   → ปฏิเสธ พร้อมบอกรูปแบบที่ถูก
schedule_content ชิ้นที่ให้ drop → ปฏิเสธ
```

> กับดักที่เจอตอนเขียน: ใส่ `isoformat()` ลงใน query string ของ PostgREST ไม่ได้ —
> `+00:00` ถูกตีความเป็นช่องว่าง แล้วตอบ 400 `invalid input syntax for timestamp`
> ต้องใช้รูปแบบ `...Z` (มี `_iso_z()` ให้ใช้แล้วใน `dvx_data.py`)

## รอบจริงบน GitHub Actions + บั๊กที่เจอจากมัน

เจ้าของตั้ง secret ครบสองที่แล้วกด Run workflow — ได้ `HTTP 200` พร้อม
`{"ok":true,"posted":0,"results":[]}` = สายต่อครบทั้ง GitHub → Vercel
(ถ้า Vercel ไม่มี secret จะเป็น 503 · ถ้าค่าไม่ตรงจะเป็น 401)

**แต่ขึ้นคำเตือน "มีชิ้นที่โพสต์ไม่สำเร็จในรอบนี้" ทั้งที่ไม่มีอะไรล้มเลย**

ต้นเหตุไม่ใช่เงื่อนไขคำเตือน แต่คือ **คำตอบมีสองรูปแบบตามเส้นทางที่วิ่ง**:

```
ไม่มีของถึงคิว  → {ok, checked_at, posted, results}          ← ขาด failed
มีของถึงคิว     → {ok, checked_at, dryRun, due, posted, failed, results}
```

workflow มองหา `"failed":0` หาไม่เจอจึงสรุปว่ามีของล้ม

แก้ที่ต้นเหตุ — ทำให้ทุกเส้นทางคืนรูปเดียวกันครบทุก field
**คำตอบที่รูปไม่คงที่ทำให้คนอ่านผลผิด ต่อให้ตัวเลขทุกตัวถูก** และแยกคำเตือนเป็นสองกรณี
(อ่านค่าไม่ได้ ≠ มีของล้มจริง) ซึ่งเดิมเหมารวมกันจนบั๊กนี้อ่านเหมือนของล้ม

## งานตั้งเวลาของ Hermes ตอนนี้มี 2 ตัว

| เวลา | งาน | ส่งไปที่ |
|---|---|---|
| ทุก 30 นาที | ตรวจคอนเทนต์ก่อนถึงมือเจ้าของ | local |
| 09:00 ทุกวัน | วางแผนปฏิทินโพสต์ | Telegram |

ตัววางแผนดูยอดขาย 7 วันกับสต็อกหน้าตู้ก่อนเลือกลำดับ — **ดันของที่ยอดโตและยังมีของ**
เชียร์ของที่หมดตู้คือจ่ายค่าโฆษณาให้คู่แข่ง

## ปฏิทินต้องมี 3 สถานะ ไม่ใช่ 2 (0ef3927)

เดิมปฏิทินมี `โพสต์แล้ว` กับ `จองเวลาแล้ว` — พอมีตัวตั้งเวลา คำว่า "จองวัน"
กลายเป็น **สองความหมายที่ต่างกันคนละเรื่อง**: ชิ้นที่ถึงเวลาแล้วยิงเอง
กับชิ้นที่ถึงเวลาแล้วเงียบเพราะยังติดอะไรอยู่ คนดูแยกไม่ออก
= เข้าใจผิดว่าของจะขึ้นเพจแล้วแต่จริง ๆ ไม่ขึ้น

เพิ่มสถานะ `โพสต์อัตโนมัติ` (สีม่วง) + บอกเหตุผลเมื่อจองวันไว้แต่จะไม่ยิง
(ยังไม่อนุมัติ / ผู้ตรวจให้ drop / ยังมีช่องว่างค้าง)

**เงื่อนไขของป้ายต้องตรงกับด่านจริงของ `publish-due` เป๊ะ ๆ ไม่งั้นป้ายโกหก**
เขียนตัวเทียบสองฝั่งแล้วรันกับข้อมูลจริง: 24 แถวตัดสินตรงกัน 24 แถว
บวกเคสสังเคราะห์ 6 แบบตรงกันหมด (ตัวเทียบอยู่ที่ scratchpad — รันซ้ำได้ทุกครั้งที่แก้ด่าน)

> ⚠ เกือบพลาด: ปุ่มเลื่อนวัน/เอาวันออก gate ด้วย `kind === "scheduled"`
> พอเพิ่ม kind ใหม่ ชิ้นที่ตั้งเวลาไว้แล้ว (ซึ่งต้องแก้วันบ่อยสุด) จะไม่มีปุ่มให้แก้
> — เพิ่ม enum แล้วต้องไล่ดูทุกที่ที่เทียบค่าเดิม

> กับดักตัวตัดฟังก์ชันตอนเขียน harness: `blockReason` มี regex `/\{[^}]{1,40}\}/`
> ตัวนับปีกกาจึงเพี้ยน ต้องตัดด้วย "บรรทัดที่เป็น `}` ตัวเดียว" แทน
