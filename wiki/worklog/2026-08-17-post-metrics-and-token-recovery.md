# กู้ token Facebook + เริ่มเก็บผลลัพธ์โพสต์

เจ้าของถามว่า Hermes เก็บยอดไลก์/คอมเมนต์/แชร์ของโพสต์ได้ไหม — พอไปเช็กของจริงก่อนตอบ
เจอเรื่องที่ใหญ่กว่าคำถาม

## 🔴 เจอก่อนอื่น: token Facebook ตายอยู่

ยิงทดสอบ 3 endpoint ด้วย token ใน `.env.local` ตายทั้งหมด:

```
OAuthException (code 200)
"Cannot call API for app 1545969993399636 on behalf of user 122113288791314224"
```

**แปลว่าตัวโพสต์อัตโนมัติที่เพิ่งเปิดไปเมื่อชั่วโมงก่อนก็จะพังด้วย** ถ้าไม่เจอตรงนี้
จะไปเจอตอนโพสต์แรกไม่ขึ้นเพจแล้วไม่มีใครรู้สาเหตุ

> บทเรียน: **เช็กปลายทางของจริงก่อนสร้างของใหม่ทับ** ถ้าลงมือเขียนตัวเก็บสถิติทันที
> จะเสียเวลาดีบักไปกับโค้ดที่ถูกอยู่แล้ว เพราะต้นตอไม่ได้อยู่ในโค้ด

กู้ด้วย `scripts/fb-token.mjs` ตามที่ [[auto-posting-level3-setup]] เขียนไว้ · APP_ID ได้จาก
ข้อความ error เอง (`1545969993399636`) ไม่ต้องไปหาในหน้าเว็บ

> ⚠️ ระหว่างกู้ เจ้าของวาง error ที่มี **APP_SECRET** ติดมาในแชท — บอกให้รีเซ็ตแล้ว
> แต่การรีเซ็ตจะทำให้ token ทุกตัวของแอปตายทันที ต้องกู้ใหม่พร้อมกัน จึงยังค้างไว้ให้ทำตอนว่าง

## Graph API v26 ให้อะไรได้จริง (ยิงทดสอบทีละ metric)

```
✅ likes · reactions (รวม+แยกชนิด) · comments · shares
✅ post_clicks · post_video_views
❌ post_impressions · post_impressions_unique · post_engaged_users · post_activity
❌ page_impressions · page_fans        ← "not a valid insights metric"
```

**ไม่มี reach ให้เก็บอีกแล้ว** จึงไม่ใส่คอลัมน์ reach ไว้ในตารางให้หลอกตา
(เขียนเหตุผลกำกับใน migration ด้วย เผื่อวันหน้ามีคนสงสัยว่าทำไมไม่มี)

## ตัดสินใจอะไรไว้

### เก็บเป็นสแนปช็อตหลายแถวต่อโพสต์

เอนเกจโตตามเวลา — โพสต์เมื่อวานกับเดือนก่อนเทียบ "ยอดปัจจุบัน" ตรง ๆ ไม่ยุติธรรม
เก็บหลายจุดแล้วเทียบ **24 ชม.แรก** ได้

⚠️ ข้อจำกัดที่เพิ่งเห็นจากข้อมูลจริง: `avg_reactions_24h` เป็น null ทั้ง 25 โพสต์
เพราะเริ่มเก็บหลังโพสต์ไปนานแล้ว — ตัวเทียบนี้จะใช้ได้เฉพาะโพสต์ที่เก็บตั้งแต่วันแรก
(เขียนไว้ใน note ของ tool แล้ว ไม่ให้เข้าใจผิดว่าเป็นบั๊ก)

### ครอบทุกโพสต์บนเพจ ไม่ใช่แค่ที่มาจากระบบ

`content_id` เป็น null ได้ตั้งใจ — ถ้าบังคับให้ผูกกับ `marketing_content` จะได้ตารางเปล่า
เพราะยังไม่มีชิ้นไหนโพสต์ผ่าน API เลย และโพสต์ที่เจ้าของทำด้วยมือก็มีค่าให้เรียนรู้

ผลคือ**เก็บได้ 25 โพสต์ทันทีในรอบแรก** ไม่ต้องรอสร้างข้อมูลใหม่

### กันสรุปเกินตัว — `enough` ต่อช่อง ไม่ใช่แค่คำเตือนรวม

รอบแรกได้ข้อมูลชี้ว่า 20:00 ดีที่สุด (12.5 รีแอ็กชัน) **แต่มาจากโพสต์แค่ 2 ชิ้น**
ค่าเฉลี่ยจาก 1-2 โพสต์คือความบังเอิญ ไม่ใช่ข้อสรุป และเป็นความมั่นใจผิด ๆ ที่อ่านดูมีข้อมูลรองรับ

จึงติดธง `enough: posts >= 3` ให้ทุกช่อง (ตามชั่วโมง/ตามรูปแบบ) และเขียนใน note ว่า
ห้ามใช้ช่องที่ `enough=false` สรุป — ทดสอบแล้ว Hermes เคารพธงนี้จริง
มันตอบเองว่า *"เวลา 20.00 มีไลก์ 12.5 แต่มีโพสต์แค่ 2 ชิ้น — สรุปไม่ได้"*

## ผลรอบแรกของจริง

```
เก็บได้ 25 โพสต์ · จากระบบ 0 ชิ้น (ทำมือหมด)
ไลก์เฉลี่ย 6.8 ต่อโพสต์
สูงสุด 20 ไลก์ — "การ์ดลูฟี่ที่ราคาแรงขนาดนี้" (13 ส.ค. 18:01) และ "5 อันดับการ์ดราคาสูง OP16"
ช่องที่ข้อมูลพอเชื่อ: 16:00 (6.8) · 17:00 (7.0) · 18:00 (6.5) — ต่างกันน้อยมาก
```

สิ่งที่ข้อมูลชี้แบบยังไม่ฟันธง: โพสต์แนว **จัดอันดับ / การ์ดแพง-แรร์** ได้ไลก์สูงกว่าค่าเฉลี่ยชัด
ส่วนเวลาโพสต์ยังแยกไม่ออกว่าต่างกันจริงหรือเป็นความผันผวน

กดรันซ้ำในชั่วโมงเดียวกัน → `saved: 0` unique index ทำงานถูก ไม่บวมข้อมูล

## กับดักทางเทคนิคที่กันไว้

**สร้าง index บน `date_trunc('hour', captured_at)` ไม่ได้** — `date_trunc` กับ `timestamptz`
เป็น STABLE ไม่ใช่ IMMUTABLE Postgres ปฏิเสธตอน create index
แก้ด้วยให้ตัวเก็บปัดชั่วโมงมาเป็นคอลัมน์ `captured_hour` แล้ว unique index บนคอลัมน์จริง

**PostgREST บอกว่าไม่มีตารางได้ 2 แบบ** — 404 `PGRST205` (ไม่อยู่ใน schema cache) กับ
`42P01` ของ Postgres · ดักแบบเดียวไม่พอ ต้องดักทั้งคู่ ไม่งั้น agent เห็น SQL error ดิบ
แล้วทำอะไรต่อไม่ถูก

### บั๊ก CI ที่เจอจากรอบแรก: job แดงทั้งที่งานสำเร็จ

รอบแรกของ workflow ได้ HTTP 200 เก็บครบ 25 โพสต์ **แต่ job ขึ้น failure**

บรรทัดสุดท้ายของ step เขียนเป็น `[ "$collected" = "0" ] && echo ...`
พอเงื่อนไขเป็นเท็จ — ซึ่งคือ**กรณีปกติ** เพราะเก็บได้ 25 — `[` คืน exit code 1
GitHub เอา exit code ของคำสั่งสุดท้ายเป็นผลของ step → แดง

**นี่คือบั๊กคลาสเดียวกับ `grep -q` ในตัวโพสต์อัตโนมัติเมื่อชั่วโมงก่อน** —
เขียนตัวตรวจแบบ shorthand แล้วผลของ "การตรวจ" ไปปนกับผลของ "งาน"

> กฎที่ควรจำ: ใน CI **ห้ามให้ `[ ... ] &&` หรือ `grep -q` เป็นคำสั่งสุดท้ายของ step**
> ใช้ `if/fi` เสมอ · ที่อยู่กลาง step ไม่กระทบ (bash ไม่ออกเมื่อ `[` ล้มใน AND-OR list)
