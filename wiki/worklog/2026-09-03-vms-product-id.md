# เราเดาว่าขายอะไร ทั้งที่บิลบอกมาตลอด

เจ้าของเทียบหน้าเว็บกับหลังบ้าน VMS วันที่ 1 ก.ย. แล้วเจอว่า **ยอดเงินตรงเป๊ะทุกตู้
แต่สินค้าคนละตัว** — หลังบ้านบอกบิล 14:05:42 ที่ [[chukes04]] คือ OP-17 (250) + OP-08 (140)
ระบบเราบันทึกเป็น NRT Jin-2 + PRB 01 Box

## ทำไมเงินถูกแต่ของผิด

เพราะมันมาจากคนละแหล่ง

- **เงิน** มาจาก `total_price` ของบิล → ถูกเสมอ
- **สินค้า** เราไม่ได้อ่านจากบิล เราไป *เดา* จาก `cart_slot` (เลขช่อง) แล้วเปิดตาราง
  `machine_stock` ถามว่า "ตอนนี้ช่องนั้นมีอะไร"

การเดาแบบนี้ถูกก็ต่อเมื่อของหน้าตู้ไม่เคยขยับ ซึ่งไม่จริง — แอดมินจัดของใหม่เมื่อไหร่
บิลทุกใบก่อนที่เราจะ sync สต็อกทัน จะถูกป้ายด้วยของ**ชุดใหม่**ย้อนหลัง

`slot_products_history` ยืนยันเวลาให้เอง: ช่อง 017/026/027/028 ของ chukes04
เปลี่ยนเป็น OP-08/OP-17 ตอน 14:19 น. ของวันที่ 1 ก.ย. — **หลัง**บิล 10:45 และ 14:05
เท่ากับ 118 จาก 143 แถวของตู้นั้น (82%) ถูกป้ายผิด ส่วนตู้ 1–3 ผิดรวมกัน 8 แถว

นี่ยังอธิบายด้วยว่าทำไม **payif กับ WW ไม่เคยเป็น** — API ของสองเจ้านั้นส่งชื่อสินค้า
มากับบิลตรง ๆ ไม่ต้องเดา มีแต่ VMS ที่เราเดา

## ของที่มีอยู่แล้วแต่ไม่เคยหยิบ

สั่งรัน sync พร้อม `dump_raw` แล้วดู payload ดิบ พบว่า API ส่งมาครบตั้งแต่แรก

```json
"cart":       ["14258", "23"],       ← รหัสสินค้ารายชิ้น
"cart_slot":  ["044", "033"],
"dispenseStatus": [{"product_id": "14258", "slot_code": "044", "status": "success"}, …],
"discount": 0, "normal_price": 560, "total_price": 560, "price_conflict": false
```

`14258` = One Piece OP-17 (250) · `23` = OP-13 (310) → **560 ตรงยอดบิลพอดี**
ลองกับบิลจริงของวันนั้นทั้ง 6 ใบที่ dump ออกมา ราคารายชิ้นสร้างยอดบิลได้ **6/6 ใบ**

> ⚠️ ตอน dump ห้ามพิมพ์ทั้ง row — ใน payload มี `qr_data`, `ksher_order_no`, `ksher_mid`
> ซึ่งเป็นข้อมูลการชำระเงิน โค้ดจึงเลือกพิมพ์เฉพาะฟิลด์ที่ใช้ออกแบบ

## แก้ยังไง

`fetch_product_lookup()` สร้าง `product_id → (sku_id, ชื่อ, ราคา)` สองชั้น
`(machine_id, product_id)` ก่อน แล้วตกไปที่ `product_id` ข้ามตู้ · อ่านรายการจาก
`dispenseStatus` ก่อน (ผูก product_id กับ slot มาให้แล้ว) ไม่มีค่อย `zip(cart, cart_slot)`

**รหัสสินค้าไม่ขยับตามช่อง** ย้ายของกี่รอบก็ยังชี้ตัวเดิม เลขช่องยังเก็บไว้อ้างอิง
และยังถอยไปเดาจากช่องได้ถ้าเจอรหัสที่ไม่รู้จัก (นับ + รายงานออกมา ไม่เงียบ)

ตรวจกับข้อมูลจริงก่อนเชื่อ: `machine_stock` ตู้ VMS มี `product_id` 233/240 ช่อง (97%)
รหัส→SKU เป็น 1:1 **ไม่ชนกันเลยสักตัว** และราคาเท่ากันทุกตู้

## ซ่อมของเก่า — และด่านที่ต้องมี

แก้ข้างหน้าอย่างเดียวไม่พอ แถวเก่าไม่หายเอง เพราะ `sales` ตั้ง `ignore_duplicates=True`
ไว้กัน sync ย้อนหลังทับประวัติ (ดู [[2026-08-31-vms-bill-split]]) — sync ซ้ำเท่าไหร่ก็ไม่ขยับ

`--repair` ยอมทับได้ เพราะตอนนี้ชี้สินค้าจาก**รหัสในบิล** ไม่ใช่สภาพตู้ตอนนี้
ซ่อมกี่รอบก็ได้คำตอบเดิม แต่ต้องมีด่าน — แตะเฉพาะบิลที่

1. ทุกบรรทัดรู้จักรหัสสินค้า (ไม่มีบรรทัดไหนต้องถอยไปเดาจากช่อง)
2. ราคารายชิ้นรวมแล้วเท่ายอดที่ตู้คิดเงินจริง

บิลที่ไม่ผ่านถูกข้ามและพิมพ์เลขบิลออกมา `drop_orphans()` เก็บกวาดแถวส่วนเกิน —
`sale_key` คือ `txid-ลำดับ` ถ้ารอบเก่า map ได้ 3 บรรทัดแต่รอบใหม่ได้ 2 แถว `-2`
จะค้างเป็นผีทำให้ยอดเกินจริง การซ่อมที่ไม่เก็บกวาดคือการสร้างปัญหาใหม่

โหมดซ่อมไม่ fallback ไป Playwright — เส้นนั้นไม่มีรหัสสินค้าให้ยึด ปล่อยไปคือทับข้อมูล
ด้วยของที่เดาจากช่องอีกรอบ = ย้อนกลับไปหาบั๊กเดิม
